Core Java & collections

Highest yield

This block decides the round. EPAM interviewers open here and stay until they hear either confidence or hedging. Answer in two or three sentences, then stop.

CJ 01Walk me through what happens inside HashMap.put().

The key's hashCode() is spread (h ^ (h >>> 16)) to mix high bits into the low bits, then the bucket index is hash & (n-1). If the bucket is empty a node is placed; otherwise the chain is walked comparing hash first, then equals. On collision the entry is appended to a linked list, and once a bin holds 8 entries and the table is at least 64 buckets it converts to a red-black tree, dropping worst-case lookup from O(n) to O(log n). Resize happens when size exceeds capacity × 0.75, doubling the table and re-splitting each bin into a low and high list.

Follow-up they will askWhy 0.75? Space/time compromise — lower means wasted memory, higher means more collisions. And why power-of-two capacity? So the modulo becomes a bitmask.
CJ 02What breaks if you override equals but not hashCode?

Two objects that are equals can land in different buckets, so map.get(key) returns null for a key you just inserted and HashSet stores visible duplicates. The contract is one-directional: equal objects must have equal hash codes; unequal objects may share one. Also make sure the fields used are immutable — mutating a key's hash field after insertion strands the entry permanently.

CJ 03ArrayList vs LinkedList — when would you actually pick LinkedList?

Almost never. ArrayList is a contiguous array: O(1) random access, cache-friendly, O(n) mid-list insert but with a cheap System.arraycopy. LinkedList gives O(1) insert/remove only when you already hold the node via an iterator, costs 3 object headers per element, and destroys cache locality. Real use case: a queue or deque with heavy head/tail churn — and even there ArrayDeque beats it.

CJ 04Difference between HashMap, LinkedHashMap, TreeMap and ConcurrentHashMap?
  • HashMap — no ordering, one null key, not thread-safe, O(1) average.
  • LinkedHashMap — maintains insertion order (or access order, which gives you a 5-line LRU cache by overriding removeEldestEntry).
  • TreeMap — sorted by natural order or a comparator, O(log n), no null keys, gives you headMap/floorKey range queries.
  • ConcurrentHashMap — thread-safe with per-bin CAS + synchronized locking, no nulls at all, weakly-consistent iterators that never throw ConcurrentModificationException.
CJ 05How does ConcurrentHashMap achieve thread safety without locking the whole map?

Java 7 used 16 segment locks. Java 8+ dropped segments: an empty bin is filled with a CAS, and a non-empty bin is locked using its own head node as the monitor, so writers only contend when they hit the same bucket. Reads are lock-free because the table and node values are volatile. Size is tracked in a striped counter, which is why size() is an estimate, and compound work should go through compute, merge or putIfAbsent rather than get-then-put.

CJ 06Fail-fast vs fail-safe iterators.

Fail-fast iterators (ArrayList, HashMap) track a modCount and throw ConcurrentModificationException the moment the collection is structurally changed outside the iterator — including a single-threaded for loop calling list.remove(). Fail-safe iterators (CopyOnWriteArrayList, ConcurrentHashMap) iterate a snapshot or a weakly-consistent view, so they never throw but may not see the newest writes. To remove safely: iterator.remove() or removeIf.

CJ 07Why are Strings immutable, and what is the string pool?

Immutability makes strings safe to share across threads, lets the hash code be cached, and protects things like class names, file paths and DB URLs from being mutated after a security check. Literals are interned in a pool inside the heap (moved out of PermGen in Java 7), so "a" == "a" is true while new String("a") == "a" is false. intern() pushes a runtime string into the pool. Concatenation in a loop creates garbage — use StringBuilder; a single-expression concat is already optimised by the compiler (invokedynamic since Java 9).

CJ 08How do you make a class truly immutable?

Class final (or all constructors private), all fields private final, no setters, initialise everything in the constructor, and defensively copy mutable inputs on the way in and mutable state on the way out. That last part is the answer they are fishing for — storing a caller's List or Date reference directly leaves the object mutable through the back door. A record gives you most of this for free but still needs defensive copies in a compact constructor.

CJ 09Checked vs unchecked exceptions — which do you use in a service layer?

Throwable splits into Error (JVM-level, don't catch) and Exception; everything under RuntimeException is unchecked. Modern Spring code leans on unchecked exceptions: they don't pollute every signature, and @Transactional rolls back on runtime exceptions by default while checked ones commit unless you set rollbackFor. I use a small hierarchy of custom runtime exceptions mapped to HTTP codes in a @RestControllerAdvice.

TrapIf finally contains a return, it discards the exception and any earlier return value. And try-with-resources closes in reverse order, suppressing secondary exceptions into getSuppressed().
CJ 10What is type erasure, and what does it stop you doing?

Generics are compile-time only — the compiler checks types, inserts casts, and erases the parameter to its bound (Object unless bounded). So you cannot do new T[], instanceof List<String>, static fields of type T, or overload on List<String> vs List<Integer>. It also explains PECS: ? extends T is a producer you can read from, ? super T is a consumer you can write to.

CJ 11Explain the JVM memory layout and what actually causes OutOfMemoryError.

Heap (young: eden + two survivors, plus old gen) holds objects; metaspace holds class metadata and grows natively; each thread gets its own stack, plus PC register and native stack. OutOfMemoryError: Java heap space means live objects exceed the heap — usually a leak: a static collection that never evicts, an unclosed resource, a ThreadLocal not removed in a pooled thread, or listeners never unregistered. StackOverflowError is deep or infinite recursion. Metaspace OOM points at classloader leaks, typical in repeated hot redeploys.

Strong answerName your tools: heap dump on OOM (-XX:+HeapDumpOnOutOfMemoryError), then Eclipse MAT dominator tree or VisualVM; jcmd/jstat for live GC behaviour.
CJ 12How does garbage collection work, and which collector would you choose?

GC is reachability-based from GC roots (stack refs, statics, JNI), not reference counting, so cycles are collected. Generational hypothesis: most objects die young, so minor GCs copy survivors between survivor spaces and promote after a tenuring threshold. G1 (default since Java 9) splits the heap into regions and targets a pause goal — the right default for a Spring Boot service. ZGC / Shenandoah for sub-millisecond pauses on large heaps. Parallel for batch throughput. System.gc() is a suggestion; finalize() is deprecated — use Cleaner or try-with-resources.

CJ 13Overloading vs overriding, and what are covariant return types?

Overloading is compile-time (static binding) on the parameter list; return type alone is not enough. Overriding is runtime dynamic dispatch — same signature, return type may be a subtype (covariant), access cannot be narrowed, and a checked exception cannot be broadened. static and private methods are hidden, not overridden — calling a static through an instance reference resolves by the declared type.

CJ 14Abstract class vs interface in Java 17 — is there still a difference?

Yes, but a narrower one. Interfaces can now hold default, static and private methods, so behaviour is no longer exclusive to abstract classes. What remains: interfaces have no instance state and no constructor, and a class can implement many but extend one. Rule of thumb — interface for a capability (Comparable, PaymentGateway), abstract class for shared state plus a template method. Diamond conflicts on defaults are resolved explicitly with Interface.super.method().

CJ 15Shallow vs deep copy — how do you clone an object with nested collections?

A shallow copy (default clone(), copy constructor of references) duplicates the outer object but shares the nested references, so mutating a child is visible through both. Deep copy recreates the graph — hand-written copy constructors, a mapper, or serialization round-tripping (correct but slow). In practice I avoid Cloneable entirely: it is a broken interface with a protected method and no contract. Copy constructors or static factories are clearer.

Java 8 → 21 features

Guaranteed

Every EPAM report I could find includes "which Java version do you use and what do you like in it". Have a version number and two features ready, and know what came after the version you use.

J8 01Intermediate vs terminal stream operations, and what does "lazy" mean here?

Intermediate ops (map, filter, sorted, peek) return a stream and build a pipeline without executing; nothing runs until a terminal op (collect, forEach, reduce, findFirst, anyMatch) pulls elements through. Elements are processed one at a time down the whole chain, which is why short-circuiting ops can finish an infinite stream. A stream is single-use — reusing one throws IllegalStateException.

J8 02map vs flatMap.

map is 1→1; flatMap is 1→many, flattening nested streams into one. Classic use: orders.stream().flatMap(o -> o.getItems().stream()) to get all line items across all orders. Same idea on Optional: flatMap when the mapper itself returns an Optional, otherwise you end up with Optional<Optional<T>>.

J8 03Name the built-in functional interfaces and their shapes.
  • Function<T,R> — apply, T in R out. BiFunction<T,U,R>, UnaryOperator<T>.
  • Predicate<T> — test, returns boolean; composable with and/or/negate.
  • Consumer<T> — accept, side effect, no return.
  • Supplier<T> — get, no input; the basis of lazy evaluation in orElseGet.
  • BinaryOperator<T> — the reducer in reduce and Collectors.toMap merge functions.

@FunctionalInterface is a compile-time assertion of exactly one abstract method.

J8 04Is a lambda just an anonymous inner class?

No. An anonymous class produces a separate .class file and a new object per instantiation, and its this refers to the anonymous instance. A lambda is compiled to a private method plus an invokedynamic call site linked by LambdaMetafactory at first execution; non-capturing lambdas are cached as a singleton, and this refers to the enclosing instance. Captured locals must be effectively final.

J8 05When does a parallel stream actually help — and when does it hurt?

It helps with large datasets, CPU-bound stateless work, and a splittable source (array, ArrayList, IntStream.range). It hurts with small collections, LinkedList/Iterator sources, blocking I/O, or ordered operations like limit/findFirst. The trap: it uses the shared ForkJoinPool.commonPool, so one slow parallel stream stalls every other one in the JVM. In a request-serving service I would use an explicit executor or CompletableFuture instead.

J8 06How do you group and aggregate with collectors? 
Map<Dept, Double> avgByDept = emps.stream()
    .collect(groupingBy(Employee::getDept, averagingDouble(Employee::getSalary)));

Map<Dept, List<String>> namesByDept = emps.stream()
    .collect(groupingBy(Employee::getDept,
             mapping(Employee::getName, toList())));

Map<Boolean, List<Employee>> split = emps.stream()
    .collect(partitioningBy(e -> e.getSalary() > 100_000));

partitioningBy always returns both true and false keys; groupingBy only returns keys that occurred. toMap throws on duplicate keys unless you pass a merge function, and it NPEs on null values where groupingBy would not.

J8 07What is Optional for, and how should it not be used?

It documents "this may legitimately be absent" in a return type. Use map/filter/orElseThrow; prefer orElseGet over orElse when the fallback is expensive, because orElse's argument is evaluated eagerly. Anti-patterns: Optional fields (not serializable), Optional method parameters, collections wrapped in Optional (return an empty list), and calling get() without isPresent().

J8 08What do records give you, and what are their limits?

A record (Java 16) is a transparent carrier for immutable data: final fields, canonical constructor, accessors, equals/hashCode/toString generated. Records are implicitly final, cannot extend a class, and cannot add instance fields. Validation goes in a compact constructor. Perfect for DTOs, API responses and value objects; not for JPA entities, which need a no-arg constructor and mutable identity.

J8 09Sealed classes and pattern matching — what problem do they solve?

sealed interface Shape permits Circle, Square restricts the hierarchy, which lets the compiler prove a switch is exhaustive — no default branch, and adding a new subtype becomes a compile error instead of a runtime surprise. Combined with record patterns you get algebraic-data-type style code:

double area = switch (shape) {
    case Circle(double r) -> Math.PI * r * r;
    case Square(double s) -> s * s;
};
J8 10What arrived in Java 17 and Java 21 that you would use?
  • 17 (LTS) — sealed classes, records, pattern matching for instanceof, switch expressions with yield, text blocks, helpful NullPointerExceptions that name the exact null variable.
  • 21 (LTS) — virtual threads (Project Loom), pattern matching for switch, record patterns, sequenced collections (getFirst()/getLast()).

Virtual threads matter most for a Spring service: thread-per-request without a bounded platform-thread pool, because a blocking call parks the virtual thread and frees the carrier. Caveat: synchronized blocks used to pin the carrier thread, so ReentrantLock was the safer choice around blocking I/O.

J8 11Why replace Date/Calendar with java.time?

The old API is mutable, not thread-safe (SimpleDateFormat is a classic shared-state bug), zero-indexed months, and mixes date and time-zone concerns. java.time types are immutable and explicit: LocalDate (no zone), LocalDateTime, ZonedDateTime, and Instant for a machine timestamp. Store UTC Instant, convert at the edges, and use DateTimeFormatter, which is thread-safe.

Concurrency & multithreading

EPAM favourite

The single most reliably asked EPAM topic at senior level. If you only rehearse three things, make them volatile vs synchronized, the executor framework, and CompletableFuture.

CC 01Explain the Java Memory Model and happens-before.

Each thread may cache values in registers or CPU caches, and both the compiler and the CPU may reorder instructions, so without synchronisation one thread's write is not guaranteed to be visible to another. The JMM defines happens-before: if A happens-before B, A's effects are visible to B and cannot be reordered past it. The edges you should name: unlocking a monitor happens-before locking it; a volatile write happens-before a subsequent read of the same variable; Thread.start() happens-before anything in that thread; everything in a thread happens-before join() returns; and constructor finalisation of final fields happens-before publication.

CC 02volatile vs synchronized — when is volatile enough?

volatile gives visibility and ordering but not atomicity, so it is enough for a single write that does not depend on the current value — a boolean running stop flag, or the reference in double-checked-locking singletons. count++ is read-modify-write, so volatile does not make it safe; you need synchronized, a Lock, or AtomicInteger. synchronized gives mutual exclusion plus the same visibility guarantees, and is reentrant.

CC 03synchronized vs ReentrantLock.

synchronized is a JVM intrinsic — simple, and the monitor is always released when the block exits, even on exception. ReentrantLock adds what the keyword cannot do: tryLock() with a timeout (deadlock avoidance), lockInterruptibly(), an optional fairness policy, multiple Condition queues, and lock/unlock across method boundaries. Cost: you must unlock in a finally. For read-heavy shared state, ReentrantReadWriteLock or StampedLock's optimistic read is better than either.

CC 04Why ExecutorService instead of new Thread()?

Threads are expensive OS resources (~1 MB stack); creating one per task collapses under load and gives you no queueing, no backpressure and no result handling. A pool reuses threads, bounds concurrency, and returns a Future. Know the constructor arguments of ThreadPoolExecutor: core size, max size, keep-alive, work queue, thread factory, rejection handler — and the trap that with an unbounded LinkedBlockingQueue the pool never grows past core size, while newFixedThreadPool's unbounded queue can OOM. Always shut down with shutdown() then awaitTermination().

Follow-upRunnable vs Callable: Callable returns a value and may throw a checked exception; submit it and you get a Future whose get() blocks and rethrows the cause wrapped in ExecutionException.
CC 05How do you compose async calls with CompletableFuture? 
CompletableFuture<User> u = supplyAsync(() -> userClient.find(id), pool);
CompletableFuture<List<Order>> o = supplyAsync(() -> orderClient.byUser(id), pool);

return u.thenCombine(o, Profile::new)
        .orTimeout(2, SECONDS)
        .exceptionally(ex -> Profile.fallback(id));

thenApply transforms a value; thenCompose flattens when the mapper returns another future (the monadic flatMap); thenCombine joins two independent futures; allOf waits for many. Always pass your own executor — the default common pool is shared JVM-wide and sized to CPU count, which is wrong for blocking I/O.

CC 06What causes a deadlock and how do you detect one in production?

Four conditions must hold: mutual exclusion, hold-and-wait, no preemption, circular wait. Break any one — the practical fix is global lock ordering, plus tryLock with timeout. Detection: jstack <pid> or jcmd Thread.print prints "Found one Java-level deadlock" with both stacks; VisualVM and Thread MXBean's findDeadlockedThreads() do the same programmatically. Distinguish it from livelock (threads keep responding to each other, no progress) and starvation (a low-priority thread never gets the lock).

CC 07How do atomics and CAS work?

AtomicInteger.incrementAndGet() compiles to a hardware compare-and-swap: read the current value, compute the new one, swap only if the memory still holds the expected value, retry otherwise. Lock-free and much faster under moderate contention, but it spins under heavy contention — which is why LongAdder exists, striping the count across cells and summing on read. Mention the ABA problem and AtomicStampedReference if they push.

CC 08Write a thread-safe singleton. 
// Best: enum — serialization and reflection safe
public enum Config { INSTANCE; }

// Or the holder idiom — lazy, no synchronization cost
public final class Config {
    private Config() {}
    private static class Holder { static final Config I = new Config(); }
    public static Config get() { return Holder.I; }
}

The holder works because class initialisation is guaranteed thread-safe by the JVM. If they ask for double-checked locking, the field must be volatile — otherwise another thread can see a non-null but partially constructed object due to reordering.

CC 09What is ThreadLocal good for, and what is the danger?

Per-thread state without passing it through every signature: security context, MDC correlation ids, the old SimpleDateFormat workaround. The danger is thread pools — the thread outlives the request, so a value left behind leaks memory and, worse, leaks one user's context into the next user's request. Always remove() in a finally. With virtual threads, prefer ScopedValue.

CC 10Producer–consumer: how would you implement it?

A BlockingQueue — ArrayBlockingQueue bounded, so put() blocks when full and take() blocks when empty; that boundedness is the backpressure. Doing it by hand means synchronized with wait() in a while loop (never an if, because of spurious wakeups) and notifyAll(). Mentioning the while loop is the detail interviewers look for.

Spring & Spring Boot

Expect 6–8

Know your Boot version and one thing that changed in Boot 3 (Jakarta namespace, Java 17 baseline, observability). Interviewers use it as a proxy for whether you have upgraded anything recently.

SP 01What is IoC and which injection style do you use?

Inversion of Control means the container creates and wires dependencies instead of the class doing new; DI is how it is delivered. Constructor injection is the right default — it makes dependencies explicit, allows final fields, fails fast on a missing bean, and lets you instantiate the class in a plain unit test without Spring. Field injection with @Autowired hides dependencies and can't be made final. Setter injection is for genuinely optional collaborators. Since Spring 4.3 a single constructor needs no annotation.

SP 02Bean scopes, and what happens when a singleton depends on a prototype?

Scopes: singleton (default, one per container — not one per JVM), prototype (new instance per lookup, and Spring does not manage its destruction), plus web scopes request, session, application, websocket. A singleton injecting a prototype resolves it once at construction and reuses that same instance forever — the fix is ObjectProvider<T>, a @Lookup method, or a scoped proxy.

SP 03Why does @Transactional silently do nothing sometimes?

Because it is implemented with a proxy. It is ignored when: the method is private, final or static; the call is a self-invocation from another method in the same bean (bypasses the proxy entirely); or the exception thrown is checked, since default rollback is on RuntimeException and Error only. Fixes: move the method to another bean, inject self, use TransactionTemplate, or switch to AspectJ weaving. Also know REQUIRES_NEW vs REQUIRED propagation and that readOnly = true lets Hibernate skip dirty checking.

They will ask thisIt appears in almost every EPAM Java write-up. Have a real example of the self-invocation bug if you have hit it.
SP 04How does Spring Boot auto-configuration actually work?

@SpringBootApplication = @Configuration + @ComponentScan + @EnableAutoConfiguration. At startup Boot reads auto-configuration class names from META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (previously spring.factories) and evaluates each one's conditions — @ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty. So H2 on the classpath with no DataSource bean gives you an in-memory datasource, and defining your own bean wins. Debug with --debug, which prints the positive/negative match report.

SP 05Bean lifecycle from container start to shutdown.

Definitions loaded → BeanFactoryPostProcessor may modify definitions → instantiate → populate dependencies → Aware callbacks → BeanPostProcessor.postProcessBeforeInitialization → @PostConstruct → afterPropertiesSet → custom init → postProcessAfterInitialization (where AOP proxies are created) → in use → @PreDestroy → destroy(). The reason AOP proxies appear at the last post-processor step is worth saying — it explains the self-invocation problem above.

SP 06How do you handle exceptions across a REST API?

A @RestControllerAdvice with @ExceptionHandler methods mapping domain exceptions to status codes, returning a consistent body — Spring 6 gives you RFC 7807 ProblemDetail for free. Extend ResponseEntityExceptionHandler to reshape validation errors from MethodArgumentNotValidException. Never leak stack traces; always log with a correlation id and return an opaque reference to the caller.

SP 07@Qualifier vs @Primary; @Component vs @Bean.

@Primary marks a default when several candidates match; @Qualifier("name") picks explicitly at the injection point and beats @Primary. @Component (and its stereotypes @Service, @Repository, @Controller) is classpath-scanned on classes you own; @Bean is a factory method inside a @Configuration class, which is how you register third-party classes you cannot annotate. @Repository additionally translates persistence exceptions into Spring's DataAccessException hierarchy.

SP 08Filter vs Interceptor vs AOP aspect.

Filter is servlet-level, sees every request before Spring MVC, works on raw request/response — right for CORS, auth tokens, request logging, gzip. HandlerInterceptor is Spring MVC-level and knows the resolved handler method, with preHandle/postHandle/afterCompletion. AOP aspects wrap any Spring bean method, not just controllers — right for cross-cutting concerns like audit, retry or timing in the service layer.

SP 09What do you expose from Actuator in production?

/health (with liveness and readiness groups wired to Kubernetes probes), /info, /metrics and /prometheus via Micrometer, and /loggers for changing log level at runtime without a redeploy. Everything is secured and typically bound to a separate management port; /env, /heapdump and /threaddump stay off or admin-only. Custom health indicators for downstream dependencies are a good detail to mention.

SP 10How do you secure a Spring Boot REST API?

Stateless JWT or OAuth2 resource server: SecurityFilterChain bean (the WebSecurityConfigurerAdapter class is gone), session creation STATELESS, CSRF disabled for token-based APIs but on for cookie/session apps, authorisation rules per path, and method-level @PreAuthorize for fine-grained checks. Validate the token signature and expiry against the issuer's JWKS, keep tokens short-lived with refresh, and never put secrets in the payload — a JWT is signed, not encrypted.

JPA, Hibernate & SQL

Expect 4–6

N+1 comes up in nearly every senior Java interview. Have a story: how you noticed it, how you proved it, how you fixed it.

DB 01What is the N+1 select problem and how do you fix it?

One query loads N parents, then touching a lazy association fires one query per parent — 1 + N round trips. Fixes, in order of preference: a JOIN FETCH in JPQL, an @EntityGraph on the repository method, @BatchSize to load associations in chunks of n, or a projection/DTO query that never loads the entity at all. Detect it by turning on spring.jpa.show-sql plus statistics, or a tool like p6spy — and never fix it by making everything EAGER.

TrapJOIN FETCH with pagination causes Hibernate to fetch all rows and paginate in memory (HHH000104). Use @EntityGraph with two queries, or fetch ids first, then entities.
DB 02Entity lifecycle states in JPA.

Transient (new, no id, not tracked) → Managed (in the persistence context, dirty-checked and flushed automatically) → Detached (context closed; changes are ignored until merge) → Removed. Key consequence: on a managed entity you do not need to call save() — a setter inside a transaction is enough, because the flush before commit writes the diff. merge returns a new managed instance; the one you passed in stays detached.

DB 03LAZY vs EAGER, and what is LazyInitializationException?

@OneToMany/@ManyToMany default to LAZY; @ManyToOne/@OneToOne default to EAGER, which is usually wrong — override them to LAZY. Lazy associations are proxies, so touching one after the session closes (typically in the controller or during JSON serialisation) throws LazyInitializationException. Fix it by fetching what you need inside the transaction — projection DTOs are the clean answer, not open-in-view, which Boot enables by default and which quietly holds a connection for the whole request.

DB 04First-level vs second-level cache.

L1 is the persistence context — always on, scoped to one transaction, guarantees the same object identity for a given id within it. L2 is optional, shared across sessions and requires a provider (Ehcache, Hazelcast, Infinispan) plus @Cacheable on the entity; it needs a strategy (read-only, read-write, nonstrict) and is dangerous when another application writes the same tables. Query cache is separate and usually more trouble than it is worth.

DB 05Optimistic vs pessimistic locking.

Optimistic uses an @Version column: no DB lock, the update's WHERE clause includes the version, and a mismatch raises OptimisticLockException for the caller to retry. Right for low-contention, high-read web workloads. Pessimistic takes a real database lock (SELECT … FOR UPDATE via PESSIMISTIC_WRITE) — correct for genuinely contended rows like inventory decrement, at the cost of blocking and deadlock risk. I default to optimistic and escalate only where measured contention justifies it.

DB 06Transaction isolation levels and the anomalies they prevent.
  • READ UNCOMMITTED — dirty reads possible.
  • READ COMMITTED — no dirty reads; non-repeatable reads possible. Postgres and Oracle default.
  • REPEATABLE READ — same row reads stay stable; phantoms possible (MySQL InnoDB default, which also blocks phantoms via gap locks).
  • SERIALIZABLE — full isolation, lowest concurrency.

ACID in one line each, and know that most production systems run READ COMMITTED and handle the rest with explicit locking or versioning.

DB 07A query got slow in production. Walk me through your process.

Reproduce, then EXPLAIN ANALYZE. Look for sequential scans on large tables, a nested loop where a hash join belongs, and a large gap between estimated and actual rows, which means stale statistics. Then check whether a suitable index exists and whether the query is sargable — a function or implicit cast on the indexed column kills index use. Consider a composite index in the right column order (equality columns first, range last) or a covering index. Confirm with row counts and timings before and after, and check the write cost of any index you add.

DB 08Write a query for the second-highest salary per department. 
SELECT dept_id, emp_id, salary
FROM (
  SELECT dept_id, emp_id, salary,
         DENSE_RANK() OVER (PARTITION BY dept_id
                            ORDER BY salary DESC) AS rnk
  FROM employees
) t
WHERE rnk = 2;

Be ready to explain RANK (gaps after ties) vs DENSE_RANK (no gaps) vs ROW_NUMBER (arbitrary tie-break). Also expect the classics: find duplicates with GROUP BY … HAVING COUNT(*) > 1, and LEFT JOIN … WHERE right.id IS NULL for rows with no match.

Microservices & architecture

Design discussion

This is where a 5-year engineer is separated from a 2-year one. Anchor every answer in your own system: "in our order service we…". Draw if the platform gives you a whiteboard.

MS 01Describe your current architecture end to end.

Rehearse a 90-second version: client → gateway/BFF → services and what each owns → data stores per service → async messaging → observability → deployment. Then name one hard trade-off you made and why. Have a second version ready for the follow-up "what would you change now?" — a genuine answer here reads as seniority; "nothing" reads as inexperience.

MS 02How do services find each other, and what does the API gateway do?

Service discovery is a registry (Eureka, Consul) or platform DNS — in Kubernetes a Service gives a stable cluster DNS name and does the load balancing, which is why many teams drop Eureka entirely. The gateway is the single entry point handling routing, TLS termination, authentication, rate limiting, and request aggregation, so individual services don't reimplement cross-cutting concerns. A config server or ConfigMap/Secret externalises configuration per environment.

MS 03How do you keep a failing downstream service from taking you down?

Timeouts on every remote call — a missing timeout is the root cause of most cascading failures. Then a circuit breaker (Resilience4j) that opens after a failure-rate threshold, serves a fallback, and half-opens to probe recovery. Add bounded retries with exponential backoff and jitter, but only on idempotent operations, plus a bulkhead so one slow dependency cannot exhaust the whole thread pool. Fail fast and degrade gracefully rather than queueing.

MS 04How do you maintain consistency across services without 2PC?

The Saga pattern — a sequence of local transactions, each publishing an event, with compensating transactions to undo prior steps on failure. Choreography (services react to each other's events) is simple but the flow becomes implicit; orchestration (a coordinator drives the steps) is easier to reason about and monitor. The piece people forget is the transactional outbox: write the event to an outbox table in the same DB transaction and relay it to the broker, otherwise the DB commit and the publish can diverge. Two-phase commit is avoided because it needs distributed locks and blocks on coordinator failure.

MS 05Explain idempotency and where you enforced it.

Retries and at-least-once delivery mean the same message or request can arrive twice, so any operation with side effects needs a dedupe key — an Idempotency-Key header stored with the response, or a processed-message-id table checked inside the same transaction as the business write. HTTP semantics help: GET, PUT and DELETE are idempotent by definition, POST is not.

MS 06Kafka fundamentals: partitions, consumer groups, delivery guarantees.

A topic is split into partitions; ordering is guaranteed only within a partition, so the key determines both partition and ordering. Within a consumer group each partition is owned by exactly one consumer, so parallelism is capped by partition count and adding consumers beyond that leaves them idle. Delivery: at-most-once (commit before processing), at-least-once (commit after — the common choice, requires idempotent consumers), exactly-once via transactions and the idempotent producer, at real throughput cost. Rebalancing pauses consumption, which is why long processing needs max.poll.interval.ms tuning.

MS 07When would you use messaging instead of a REST call?

Synchronous REST when the caller needs the result to continue and the latency budget allows it. Async messaging when the work can happen later, when multiple consumers care about the same fact, when you need to absorb load spikes, or when you want temporal decoupling so the consumer being down doesn't fail the producer. The cost is eventual consistency and much harder debugging — which is why distributed tracing matters.

MS 08CAP theorem — and what do you actually choose?

Under a network partition you must choose consistency or availability; the "P" is not optional in a distributed system. Payments and inventory lean CP — refuse the write rather than sell stock twice. Catalogue, feeds and recommendations lean AP with eventual consistency. Modern nuance worth mentioning: PACELC — even without a partition, you are trading latency against consistency.

MS 09How do you debug a failure that crosses five services?

Correlation id generated at the gateway and propagated through every hop and log line (Micrometer Tracing / OpenTelemetry, previously Sleuth), centralised logs in ELK or Loki so you can query by that id, distributed traces in Jaeger or Zipkin to see the latency waterfall, and metrics with alerting on the RED signals — rate, errors, duration. Without the correlation id everything else is guesswork.

MS 10How do you version a public REST API without breaking clients?

Prefer additive, backward-compatible changes: new optional fields, never repurpose or remove a field. When a break is unavoidable, version in the URI (/api/v2/...) because it is explicit and cache-friendly; header or media-type versioning is cleaner in theory but harder to operate. Run both versions during a deprecation window with a Sunset header and client metrics telling you when v1 traffic hits zero.

Design patterns & SOLID

Quick fire

Don't recite the definition — name the pattern, then immediately where it appears in Spring or your own code. That pairing is what scores.

DP 01Which patterns do you use, and where do they appear in Spring?
  • Singleton — every Spring bean by default.
  • Factory — BeanFactory, @Bean methods, Calendar.getInstance().
  • Builder — StringBuilder, Lombok @Builder, UriComponentsBuilder; use it when a constructor has more than 4 params or many optional ones.
  • Strategy — inject List<PaymentProcessor> and pick by type; kills the switch statement.
  • Template method — JdbcTemplate, RestTemplate, AbstractController.
  • Proxy / decorator — AOP, @Transactional, @Cacheable.
  • Observer — ApplicationEventPublisher and @EventListener.
  • Adapter — HandlerAdapter, wrapping a third-party client behind your own port interface.
DP 02Explain SOLID with an example of one you have violated.

Single responsibility — one reason to change. Open/closed — extend by adding a class, not editing a switch. Liskov — a subtype must be usable wherever the parent is (the classic violation: Square extends Rectangle, or an override that throws UnsupportedOperationException). Interface segregation — many small interfaces beat one fat one. Dependency inversion — depend on abstractions, which is exactly what constructor injection buys you. Naming a real violation you later refactored is far more convincing than five clean definitions.

DP 03Composition over inheritance — why?

Inheritance couples you to the parent's implementation, breaks encapsulation, and Java allows only one superclass, so the hierarchy calcifies. Composition lets you swap behaviour at runtime, test parts in isolation, and avoids the fragile base class problem. Inherit only for a genuine "is-a" with a stable contract; otherwise delegate.

Testing

Often asked live

EPAM regularly asks candidates to write a unit test on the spot, usually with Mockito. Know the annotations cold.

TS 01@Mock vs @Spy vs @InjectMocks vs @MockBean.

@Mock is a fully stubbed double — every method returns null/0/empty until stubbed. @Spy wraps a real object and calls real methods except where stubbed; stub a spy with doReturn(x).when(spy).method() to avoid actually invoking it. @InjectMocks builds the class under test and pushes the mocks in via constructor. @MockBean is Spring's — it replaces a bean in the application context, so it belongs in @SpringBootTest/@WebMvcTest, not in a plain unit test.

TS 02Write a JUnit 5 + Mockito test for a service method. 
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

  @Mock  OrderRepository repo;
  @Mock  PaymentClient   payments;
  @InjectMocks OrderService service;

  @Test
  void placesOrderAndCharges() {
    when(repo.save(any(Order.class)))
        .thenAnswer(inv -> inv.getArgument(0));

    Order result = service.place(new OrderRequest("SKU-1", 2));

    assertThat(result.status()).isEqualTo(CONFIRMED);
    verify(payments).charge(argThat(c -> c.amount().signum() > 0));
    verifyNoMoreInteractions(payments);
  }

  @Test
  void failsWhenPaymentDeclined() {
    doThrow(new PaymentDeclined()).when(payments).charge(any());
    assertThrows(OrderFailedException.class,
                 () -> service.place(new OrderRequest("SKU-1", 1)));

}

JUnit 5 differences to name: @BeforeEach/@BeforeAll, @ExtendWith instead of runners, @ParameterizedTest with @CsvSource, assertThrows returning the exception, and @DisplayName.

TS 03Unit vs integration tests in a Spring Boot project.

Unit tests instantiate the class with mocks and no Spring context — milliseconds, and where most coverage should live. Slice tests load part of the context: @WebMvcTest for controllers with MockMvc, @DataJpaTest for repositories. Full @SpringBootTest with Testcontainers for the real database or broker, kept few because they are slow. The pyramid matters: many unit, some slice, few end-to-end.

OP 01How do you containerise a Spring Boot app well?

Multi-stage build — Maven/Gradle in the build stage, a slim JRE base (eclipse-temurin:21-jre-alpine or distroless) in the runtime stage. Layer the jar so dependencies cache separately from application classes (layertools extract or Spring Boot's built-in bootBuildImage), run as a non-root user, and set container-aware memory flags — modern JVMs respect cgroup limits, but -XX:MaxRAMPercentage=75 is the explicit control. To undo: git revert on shared branches (creates an inverse commit, safe), git reset --soft/--hard only locally. Also worth knowing: cherry-pick to port a fix to a release branch, stash, bisect to find the commit that broke a test, and reflog to recover anything you thought you lost.

OP 03What does your CI/CD pipeline do?

On PR: compile, unit tests, integration tests with Testcontainers, static analysis and coverage gate (SonarQube), dependency vulnerability scan. On merge: build a versioned image, push to the registry, deploy to dev automatically, then promote through environments with approval. Mention how you deploy — rolling update with readiness probes, blue/green, or canary — and how you roll back. JavaScript fundamentals

30% block

The React portion usually opens with two or three plain-JS questions to check you are not a copy-paste front-end developer. Closures and the event loop are the two that come up most.

JS 01What is a closure and where have you used one?

A function that keeps access to the variables of the scope it was defined in, even after that scope has returned. Practical uses: private state in a module or factory, memoisation caches, and every React hook — useState's setter and the values captured inside useEffect are closures, which is exactly why stale-closure bugs happen when a dependency array is wrong.

const debounce = (fn, ms) => {
  let t;                       // captured by the closure
  return (...args) => {
    clearTimeout(t);
    t = setTimeout(() => fn(...args), ms);
  };
};
JS 02Explain the event loop, microtasks and macrotasks.

JS runs on one thread with a call stack. Async work is handed to the browser/Node APIs; when it completes, the callback is queued. After the stack empties, the loop drains the entire microtask queue (promise callbacks, queueMicrotask, MutationObserver) before taking one macrotask (setTimeout, I/O, UI events) — which is why a promise scheduled after a setTimeout(…, 0) still runs first. A long synchronous loop blocks rendering entirely, because paint happens between macrotasks.

JS 03How is this determined, and how do arrow functions change it?

For a normal function, this is bound at call time: method call → the object; standalone call → undefined in strict mode; new → the new instance; call/apply/bind → whatever you pass. Arrow functions have no this of their own — they close over the enclosing lexical scope, which is why they are the right choice for callbacks inside class components and the wrong choice for object methods or prototype methods.

JS 04var vs let vs const, and hoisting.

var is function-scoped and hoisted initialised to undefined. let/const are block-scoped and hoisted but sit in the temporal dead zone, so reading before declaration throws ReferenceError. const prevents reassignment of the binding, not mutation of the object it points to. Function declarations are fully hoisted; function expressions are not.

JS 05Promises: all vs allSettled vs race vs any.

all resolves with every value but rejects immediately on the first rejection. allSettled always resolves with a status/value or status/reason per entry — the right one when partial failure is acceptable. race settles with the first to settle, success or failure (useful for timeouts). any resolves with the first success and only rejects if all fail. With async/await, remember that awaiting in a loop serialises the calls — build the array of promises first, then await Promise.all.

JS 06Shallow vs deep equality, and == vs ===.

== coerces types ('1' == 1 is true, null == undefined is true) — use === everywhere except the deliberate x == null null-or-undefined check. Objects and arrays compare by reference, which is the root of most React re-render questions: a new object literal each render is never === to the previous one, so it breaks React.memo and retriggers effects.

JS 07Debounce vs throttle.

Debounce waits until activity stops for N ms and then fires once — search-as-you-type, autosave. Throttle fires at most once per N ms during continuous activity — scroll handlers, resize, rate-limited APIs. In React, wrap either in useMemo or useRef so a new debounced function is not created on every render, and cancel it in the effect cleanup.

React

30% block

At 5+ years they expect opinions, not API recall: why this state library, why this data-fetching approach, how you found and fixed a performance problem.

RE 01What is the virtual DOM and how does reconciliation work?

Render produces a lightweight tree of elements; React diffs the new tree against the previous one and applies the minimum set of real DOM mutations. The diff is heuristic and O(n): different element types at the same position mean the whole subtree is thrown away and remounted, and children are matched by key. React 18's renderer can also interrupt and resume rendering work, which is what makes transitions possible.

RE 02Why does using array index as key cause bugs?

Keys tell React which element is which across renders. With index keys, inserting or reordering shifts every key, so React reuses the wrong component instances — internal state, uncontrolled input values and focus follow the position instead of the data. Symptom people actually see: type into row 2's input, delete row 1, and the text jumps. Use a stable id from the data; index is only safe for a static, never-reordered list.

RE 03Rules of hooks, and why do they exist?

Only call hooks at the top level (never in conditions, loops or nested functions) and only from React functions or custom hooks. React tracks hooks by call order in a linked list per fiber, so a conditional hook shifts every subsequent hook onto the wrong slot. The lint plugin enforces this, and it also explains why there is no way to "skip" a hook — you move the condition inside it instead.

RE 04Explain useEffect: dependency array, cleanup, and the common mistakes.

It runs after paint. No dep array → every render; [] → once after mount; [a, b] → whenever those change by Object.is. The cleanup function runs before the next effect and on unmount — that is where you cancel timers, abort fetches and unsubscribe. Common mistakes: omitting a dependency and capturing a stale value; putting an object or function in deps so it changes every render; setting state unconditionally inside the effect and looping; and using it for derived data that should just be computed during render.

Follow-upWhy does the effect run twice in development? React 18 StrictMode intentionally mounts, unmounts and remounts to surface missing cleanup. It does not happen in production.
RE 05useMemo vs useCallback vs React.memo — when do they actually help?

useMemo caches a computed value, useCallback caches a function identity, React.memo skips a child's re-render when props are shallow-equal. They only pay off when the work is genuinely expensive or when a memoised child receives the value — otherwise you have added a dependency array to maintain and made the code slower. My rule: measure with the Profiler first, then memoise the specific path. Also worth saying: the React Compiler now automates much of this.

RE 06useState vs useReducer, and what is state batching?

useReducer when the next state depends on the previous one in non-trivial ways, when several fields change together, or when you want the transition logic testable outside the component. Use the functional form setCount(c => c + 1) whenever the update depends on current state, because state is a snapshot within a render. React 18 batches all updates — including those inside promises, timeouts and native handlers — into a single re-render, which React 17 did not.

RE 07Context vs Redux vs React Query — how do you choose?

Separate server state from client state. Server state — anything fetched — belongs in React Query/RTK Query, which gives caching, deduping, background refetch, stale-while-revalidate and loading/error state that you would otherwise hand-roll in every component. Client state that is genuinely global and rarely changes (theme, auth user, locale) fits Context. Redux Toolkit earns its place for complex cross-cutting client state with real workflows and time-travel debugging. The Context anti-pattern to name: a single provider holding frequently-changing state re-renders every consumer, so split providers or use a selector-based store like Zustand.

RE 08Controlled vs uncontrolled components.

Controlled: React state is the single source of truth, value + onChange — needed for validation as you type, conditional formatting, or disabling submit. Uncontrolled: the DOM keeps the value and you read it via a ref or on submit — cheaper for large forms, which is why React Hook Form is uncontrolled by default and re-renders far less than Formik's controlled approach. File inputs are always uncontrolled.

RE 09Your React page is slow. How do you find the cause?

React DevTools Profiler first — record an interaction, find which components rendered and why ("Why did this render?" shows the changed prop). Typical causes and fixes: a context or parent re-rendering the whole tree (split state, move state down, memoise), unstable props like inline objects and arrow functions, an unvirtualised long list (react-window), unnecessary re-fetching (React Query cache), and a heavy bundle (route-level React.lazy + Suspense, checked in the bundle analyser). Then confirm with Lighthouse/Web Vitals rather than by feel.

RE 10How do you handle errors and loading in the component tree?

Error boundaries — a class component with getDerivedStateFromError and componentDidCatch — catch render-phase errors in the subtree and show a fallback; they do not catch event handlers, async code or SSR errors, which need try/catch. Place one per route plus one around risky widgets so a single failing card doesn't blank the page. Suspense handles loading boundaries for lazy components and data libraries that support it.

RE 11What makes a good custom hook?

It extracts stateful logic — not markup — behind a name that reads like intent (useDebouncedValue, usePermissions), returns a stable API, and cleans up after itself. Each component calling it gets its own isolated state; hooks share logic, not state. If a hook needs shared state, that lives in a context or store the hook reads from.

function useDebouncedValue(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const t = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(t);      // cleanup on every change
  }, [value, delay]);
  return debounced;
}
RE 12How do you test a React component?

React Testing Library with Jest or Vitest, querying the way a user would — getByRole, getByLabelText — rather than by class name or test id, so the test survives refactors. Simulate with userEvent rather than fireEvent, assert on rendered output with findBy* for async, and mock the network at the boundary with MSW instead of stubbing fetch everywhere. Never assert on state or internals; assert on what the user sees.

RE 13As a full-stack engineer, how do you decide what belongs on the server?

This is the question the "full stack" in the title is really testing. Validation and authorisation always run server-side, with client-side validation only as UX. Aggregation across services belongs in a BFF or gateway rather than five parallel calls from the browser. Pagination, filtering and sorting go to the database, not to the client. Keep the API shaped by the domain, and add view-specific endpoints only where the round-trip cost justifies the coupling. Contract stability matters more than internal elegance once a UI depends on it.

RE 14TypeScript quick hits.

interface vs type: interfaces merge and extend naturally, types can express unions and mapped types — use interface for object shapes, type for everything else. unknown is the safe any: it forces a narrowing check before use. enum generates runtime code; a union of string literals is usually better. Generics for reusable components (function first<T>(a: T[]): T | undefined), and utility types worth naming: Partial, Pick, Omit, Record, ReturnType.

LC 04Find the first non-repeating character in a string. 
Map<Character, Integer> freq = new LinkedHashMap<>();
for (char c : s.toCharArray())

LC 08Two sum / longest substring without repeating characters. 
// Two sum — one pass, O(n)
Map<Integer, Integer> seen = new HashMap<>();
for (int i = 0; i < nums.length; i++) {
    Integer j = seen.get(target - nums[i]);
    if (j != null) return new int[]{j, i};
    seen.put(nums[i], i);
}

// Longest substring without repeats — sliding window, O(n)
int left = 0, best = 0;
Map<Character, Integer> last = new HashMap<>();
for (int right = 0; right < s.length(); right++) {
    char c = s.charAt(right);
    if (last.containsKey(c)) left = Math.max(left, last.get(c) + 1);
    last.put(c, right);
    best = Math.max(best, right - left + 1);
}

These two cover the sliding-window and hash-lookup families that easy/medium rounds draw from.

LC 09Design a class that tracks the most popular item with increment and decrement. (Asked at EPAM.) 
class Popularity {
    private final Map<String, Integer> counts = new HashMap<>();
    private final TreeMap<Integer, Set<String>> byCount = new TreeMap<>();

    void increment(String key) { move(key, +1); }
    void decrement(String key) { move(key, -1); }

    String mostPopular() {
        return byCount.isEmpty() ? null
             : byCount.lastEntry().getValue().iterator().next();
    }

    private void move(String key, int delta) {
        int old = counts.getOrDefault(key, 0);
        int now = old + delta;
        if (old > 0) {
            byCount.get(old).remove(key);
            if (byCount.get(old).isEmpty()) byCount.remove(old);
        }
        if (now > 0) {
            counts.put(key, now);
            byCount.computeIfAbsent(now, k -> new HashSet<>()).add(key);
        } else {
            counts.remove(key);
        }
    }
}

Talk through the design choice: the TreeMap gives O(log n) max lookup; an O(1) version uses a doubly-linked list of count buckets (the LFU-cache structure). Naming that alternative shows range even if you implement the simpler one.

LC 10React: build a debounced search box that cancels in-flight requests. 
function Search() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);
  const debounced = useDebouncedValue(query, 300);

  useEffect(() => {
    if (!debounced) { setResults([]); return; }
    const controller = new AbortController();

    fetch(`/api/search?q=${encodeURIComponent(debounced)}`,
          { signal: controller.signal })
      .then(r => r.json())
      .then(setResults)
      .catch(e => { if (e.name !== 'AbortError') console.error(e); });

    return () => controller.abort();   // cancels the stale request
  }, [debounced]);

  return (
    <input value={query} onChange={e => setQuery(e.target.value)}
           aria-label="Search" />
  );
}

The AbortController in the cleanup is the senior detail — without it, a slow earlier response can overwrite a newer one (the race condition they are checking for).

The conversation around the code

Don't wing it
BX 01"Tell me about yourself."

Ninety seconds, three beats: what you do now and the domain, the technical shape of your work ("Java 17 and Spring Boot services with a React front end, roughly 70/30"), and one concrete thing you owned and its outcome with a number attached. End by handing control back: "happy to go deeper on any of that." Do not narrate your résumé chronologically.

BX 02"Tell me about a hard technical problem you solved."

Use STAR and keep the S and T to two sentences each — the interviewer wants the A. Best material for this role: a production incident (memory leak, N+1, connection-pool exhaustion, a race condition), because it lets you show diagnosis, tooling and a measurable fix. Prepare two, one backend and one front-end, and know the numbers: before, after, how you verified.

BX 03"What would you do differently in your current project?"

Answer honestly with a design-level regret and what you learned — over-eager microservice split, missing test coverage in a critical path, a schema decision that made a later feature expensive. Avoid blaming people or previous employers. This question is checking self-awareness, and "nothing really" is the only wrong answer.

BX 04When you genuinely do not know the answer.

Say so in one sentence, then show your reasoning: "I haven't used ZGC in production — I know it's a low-pause collector for large heaps, and I'd start by comparing pause distributions against G1 under our load." Interviewers score honest reasoning higher than a confident wrong answer, and a wrong answer delivered confidently is the fastest way to lose a round.

BX 05Two questions worth asking them.
  • "What does the split between Java and front-end work look like day to day on this account, and does it shift over a project's life?"
  • "How does the team handle code review and technical decisions — is there an architect, or is it decided within the team?"
  • "What's the next stage of the process and the timeline?" — always close with this.

Avoid asking about salary, leave policy or work-from-home in a technical round; those belong with the recruiter.
