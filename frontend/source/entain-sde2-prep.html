6. Java Concepts I — Memory management, end to end#

Q4Stack vs heap — what actually goes where?

  • Stack — primitives declared as locals, and references to objects. Per-thread, so inherently thread-safe. Allocation is a pointer bump; deallocation is automatic when the frame pops. Fast and LIFO. Sized with -Xss (commonly 512 KB–1 MB per thread).
  • Heap — every new, every array, every boxed value, every lambda capture that escapes. Shared, so it needs synchronisation and a garbage collector.
void demo() {
    int x = 42;                 // x itself: stack
    int[] a = new int[10];      // 'a' (reference): stack. The array: heap.
    Point p = new Point(1, 2);  // 'p': stack. Point object: heap.
}                               // frame pops; array and Point become unreachable

The follow-up they hope you miss — "an object's fields live on the heap even if they're primitives, because they're part of the object. Only local primitives sit on the stack." And: escape analysis means the JIT may prove an object never escapes the method and scalar-replace it — effectively stack-allocating it. So "objects are always on the heap" is true of the spec, not always of the running machine.

Q5Is Java pass-by-value or pass-by-reference?

Always pass-by-value. For objects, the value being copied is the reference. That's the whole answer — but say the second half, because "pass by reference" is the wrong-answer trap.

void mutate(StringBuilder sb) { sb.append("x"); }  // caller SEES this
void reassign(StringBuilder sb) { sb = new StringBuilder("y"); } // caller does NOT

In mutate, the copied reference points at the same heap object, so mutation is visible. In reassign, you repoint the local copy; the caller's reference is untouched.

Closing line — "if Java were pass-by-reference, a classic swap(a, b) would work. It can't be written in Java. That's the proof."

Q6Explain the generational heap and why it exists.

The weak generational hypothesis — the overwhelming majority of objects die young. So instead of scanning the whole heap, collect the young part often and cheaply, and the old part rarely.

  • Eden — where new allocates (via a thread-local allocation buffer, so it's a pointer bump with no lock).
  • Survivor S0 / S1 — a Minor GC copies the live objects out of Eden into the empty survivor space; Eden is then wholesale empty. Objects ping-pong between S0 and S1, aging by one each cycle.
  • Old / Tenured — once an object survives MaxTenuringThreshold cycles (default 15 on HotSpot), it's promoted. Large objects can be allocated straight here.

The payoff: Minor GC is a copying collector over live objects only. If 98% of Eden is garbage, the cost is proportional to the 2% that survives, not to the size of Eden. Dead objects cost nothing to collect.

Premature promotion is the pathology to name. If survivor spaces are too small, objects that would have died get promoted to Old, and now only a Major GC can reclaim them. Symptom: Old gen growing steadily under steady load, with frequent full GCs. That's a sizing bug, not a leak.

Q7How does the garbage collector decide an object is garbage?

Reachability from GC roots — not reference counting. An object is garbage if there is no path to it from any root.

GC roots are:

  • Local variables and parameters in every live thread's stack frames
  • static fields of loaded classes
  • Active Java threads themselves
  • JNI global and local references
  • Objects held as monitors (currently synchronized on)
  • Classes loaded by the bootstrap classloader

The collector does a mark phase from those roots, then reclaims everything unmarked.

Why this matters practically — "reference counting can't collect cycles; reachability can. Two objects pointing at each other with nothing else pointing at them are both unreachable, so both are collected. That's why a doubly-linked list or a parent↔child object graph isn't a leak in Java, but would be in a naive refcounted runtime."

And the corollary you should volunteer: "a memory leak in Java is never about forgetting to free. It's about accidentally staying reachable." That one sentence sets up every leak question in this section.

Q10What is a stop-the-world pause, and what's a safepoint?

A STW pause is a window where all application threads are suspended so the GC can work on a stable object graph. To suspend them, the JVM brings every thread to a safepoint — a known instruction boundary (method returns, loop back-edges, allocation sites) where the thread's stack can be walked accurately.

The senior detail: time-to-safepoint. A long counted loop with an int counter may be compiled without a safepoint poll, so that thread can't be stopped and every other thread waits for it. You then see a long pause that GC logs attribute to GC but that GC didn't cause. Diagnose with -XX:+PrintSafepointStatistics (older) or -Xlog:safepoint (JDK 9+). Fix: use a long counter, or break the loop up.

Also worth naming: safepoints are used for more than GC — biased-lock revocation, deoptimisation, thread dumps and some JFR operations all use them.

Q11What causes a memory leak in Java, if the GC reclaims everything unreachable?

A Java leak is unintended reachability — objects you're finished with, still on a path from a GC root. The GC is working perfectly; you've just told it, accidentally, that you still care.

The canonical causes — know all of these, name three unprompted:

  1. Static collections that only grow. A static Map used as a cache with no eviction is a leak with a nice name. Statics are GC roots for the life of the classloader.
  2. Unregistered listeners / callbacks. You add an observer and never remove it; the subject holds it forever.
  3. ThreadLocal in a pooled thread. The value is reachable from the thread, and pool threads never die. See Q12.
  4. Unclosed resources. Streams, connections, ResultSets — each holds native buffers and often a chain of references.
  5. Inner-class / lambda capture. A non-static inner class holds an implicit reference to its enclosing instance. A long-lived callback then pins a whole heavyweight object.
  6. Mutated keys in a HashMap. Mutate a field used in hashCode after insertion and the entry becomes unreachable to you but perfectly reachable to the GC. Unremovable garbage.
  7. ClassLoader leaks in app servers on redeploy — one lingering static reference into old classes keeps an entire classloader, and every class it loaded, alive in Metaspace.
  8. Interned strings and off-heap buffers — String.intern() on unbounded user input; DirectByteBuffer whose owner is retained.

Have one story ready. This is the question where a real production anecdote is worth more than the list. Shape: symptom (Old gen sawtooth that never returned to baseline) → tool (heap dump, MAT dominator tree) → culprit (the actual retaining path) → fix → what you changed so it couldn't recur (a bounded cache, an alert on Old gen after GC).

Q12Why is ThreadLocal a classic leak in a thread pool?

Each Thread owns a ThreadLocalMap. Its keys are weak references to the ThreadLocal object, but its values are strong. So when the ThreadLocal itself becomes unreachable, the key clears — but the value stays strongly held by the map until that slot is next touched.

In a ThreadPoolExecutor or a Tomcat request thread, the thread is recycled, never destroyed. So the value survives across unrelated requests — a leak, and in a multi-tenant system a correctness and security problem too: request B can read request A's context.

try {
    CONTEXT.set(userContext);
    handle(request);
} finally {
    CONTEXT.remove();   // not set(null) — remove() clears the entry
}

set(null) leaves a live entry holding a null value; remove() deletes the entry. Always remove(), always in a finally.

If they're on Java 21: ScopedValue (preview) is the modern answer — immutable, explicitly scoped by ScopedValue.where(...).run(...), so it can't leak past its block and works correctly with virtual threads.

Q14What does finalize() do, and what should you use instead?

finalize() was called by the GC before reclaiming an object. It is deprecated since Java 9 and removed from use in Java 18+, and you should never write one. Why it's broken:

  • No guarantee it ever runs, and no guarantee of when.
  • It makes objects survive at least two GC cycles — one to discover finalization is needed, one to actually collect — so it directly worsens GC.
  • Finalization runs on a single unbounded-queue daemon thread; if it blocks, objects pile up until OOM.
  • A finalizer can resurrect the object by storing this somewhere reachable.
  • Exceptions in a finalizer are swallowed.

Use instead: try-with-resources and AutoCloseable for anything deterministic — that's the answer 95% of the time. For a genuine native-resource safety net, java.lang.ref.Cleaner with a cleanup action that doesn't capture the object (capture it and the object is never collected, so the cleaner never runs).

Q15Where does the String pool live, and how does intern() work?

  • String literals are interned automatically at class load. Since Java 7 the pool moved from PermGen to the heap, which means interned strings are now ordinary garbage-collectable objects.
  • s.intern() returns the canonical pooled instance, adding s to the pool if absent.
String a = "bet";                    // pooled literal
String b = "bet";                    // same object
String c = new String("bet");        // new heap object
a == b;            // true
a == c;            // false
a == c.intern();   // true

Never intern unbounded user input. Interning every incoming bet ID or session token grows the pool without limit — a leak with a hash-table performance cliff attached. And the pool is sized by -XX:StringTableSize; a too-small table with millions of entries turns O(1) lookups into long bucket walks.

Compile-time constant folding is a good detail: "be" + "t" is folded to the literal "bet" at compile time and pooled, but "be" + variable builds a new object at runtime.

Q18StackOverflowError vs OutOfMemoryError?

StackOverflowError — a single thread's stack exceeded -Xss. Cause is almost always unbounded recursion, mutual recursion, or a cyclic toString()/equals(). Fix the recursion; raising -Xss just moves the failure.

OutOfMemoryError — a shared memory area is exhausted; the whole JVM is affected.

Both extend Error, not Exception. Don't catch them to "keep going" — after an OOM the JVM's state is unreliable and other threads may already have failed mid-operation. The correct response is to dump, exit, and let the orchestrator restart you. Catching StackOverflowError is occasionally defensible at a parser boundary; catching OutOfMemoryError almost never is.

Q19What are TLABs and escape analysis?

TLAB — Thread-Local Allocation Buffer. Each thread gets its own private chunk of Eden. Allocation inside it is a pointer bump with no synchronisation, which is why object allocation in Java is often cheaper than malloc. When a thread's TLAB is full it grabs another (that part does synchronise). Objects too large for a TLAB go straight to shared Eden or Old.

Escape analysis. C2 (and now Graal) proves whether an object can be observed outside its allocating method. If it can't:

  • Scalar replacement — the object is dissolved into its fields, held in registers or the stack. It's never allocated at all.
  • Lock elision — synchronisation on a non-escaping object is removed entirely.

Why to mention it — "it's the reason micro-optimising away small short-lived objects is usually wasted effort: the JIT often removes them for me. I'd rather write clear code and let profiling tell me where allocation actually hurts." That's the right seniority signal: you know the mechanism and when not to act on it.

Q20What is the Java Memory Model, and what does happens-before mean?

The JMM is the contract that says when a write by one thread is guaranteed visible to a read by another. Without it, the compiler, the JIT and the CPU are all free to reorder and cache — and each of them does.

happens-before is the ordering relation. If A happens-before B, A's effects are visible to B. The edges you should be able to list:

  • Program order within a single thread.
  • Monitor lock — unlocking a monitor happens-before any later lock of the same monitor.
  • Volatile — a write to a volatile happens-before every later read of it.
  • Thread start — Thread.start() happens-before anything in that thread.
  • Thread join — everything in a thread happens-before another thread's successful join() on it.
  • Final fields — correctly constructed final fields are visible without synchronisation.
  • Transitivity — A hb B and B hb C implies A hb C.

The point to land: "volatile gives visibility and ordering, but not atomicity. volatile int count; count++ is still a broken read-modify-write. For that I need AtomicInteger, a lock, or an LongAdder under contention." Reported Entain rounds ask multithreading in two separate stages — this is the line that shows you understand it rather than remember it.

Q21Why is double-checked locking broken without volatile?

private static volatile Singleton instance;   // volatile is load-bearing

static Singleton get() {
    if (instance == null) {                    // no lock on the hot path
        synchronized (Singleton.class) {
            if (instance == null) {
                instance = new Singleton();
            }
        }
    }
    return instance;
}

instance = new Singleton() is three steps: allocate, run the constructor, assign the reference. Without volatile, steps 2 and 3 can be reordered. Another thread then sees a non-null reference to a partially constructed object and uses it. volatile forbids that reordering and publishes the constructor's writes.

The better answers to offer — an enum singleton (serialization- and reflection-safe, initialised by the classloader), or the holder idiom: a private static nested class holding the instance, which the JVM initialises lazily and thread-safely with no synchronisation cost at all. If you're on Spring, the right answer is usually "the container manages the lifecycle; I don't hand-roll singletons."

Q22Production is throwing OOM. Walk me through what you do.

This is the highest-value question in this section, because it's the one where you sound like someone who has actually been on call. Answer it as a sequence, not a list of tools.

  1. Stabilise first. Is it one pod or all of them? Roll back if a deploy correlates. Customers first, root cause second.
  2. Read the error text. The variant (Q17) already narrows it to heap, Metaspace, threads, or direct memory.
  3. Look at the GC log before the dump. -Xlog:gc*:file=gc.log:time,uptime,level,tags. The signature you want is Old-gen occupancy after each Full GC. Sawtooth returning to a flat baseline = healthy, just busy. Baseline creeping upward monotonically = leak.
  4. Get the heap dump. jcmd <pid> GC.heap_dump /path/dump.hprof, or the one you already captured with -XX:+HeapDumpOnOutOfMemoryError.
  5. Open it in Eclipse MAT. Run the Leak Suspects report, then the dominator tree — it shows what's retaining memory, not just what's big. Then "Path to GC Roots, excluding weak/soft references" on the top suspect. That path is the bug.
  6. Confirm the hypothesis in code, fix, and add a regression guard — a bounded cache, a metric on the collection's size, an alert on post-GC Old-gen occupancy.

Tools to name, with what each is for: jcmd (the modern front door — VM.native_memory, GC.heap_info, Thread.print), jmap/jstat, JFR (-XX:StartFlightRecording) for low-overhead always-on profiling, JDK Mission Control, Eclipse MAT for dumps, async-profiler for allocation flame graphs, and Native Memory Tracking (-XX:NativeMemoryTracking=summary) when RSS exceeds heap and you suspect off-heap.

The distinction that earns the mark: "the first thing I establish is whether it's a leak or a capacity problem, because the fixes are opposite. A leak needs a code change; more heap just delays it and makes the eventual Full GC longer. Post-GC Old-gen occupancy over time is the measurement that tells them apart."

Q23How do you size a JVM running in a container?

  • Modern JVMs are container-aware (UseContainerSupport, on by default since 10 and backported to 8u191) — they read cgroup limits rather than the host's.
  • Prefer -XX:MaxRAMPercentage (e.g. 70–75) over a hard -Xmx, so the JVM tracks the container limit when it changes.
  • Leave real headroom. Heap is not RSS. Budget for Metaspace, thread stacks, code cache, GC structures and direct buffers — typically 25–30% of the limit.
  • Set -XX:MaxMetaspaceSize explicitly (Q16), and cap -XX:MaxDirectMemorySize if you use Netty or NIO heavily.
  • Check -XX:ActiveProcessorCount if CPU limits are fractional — GC and ForkJoinPool thread counts derive from it, and getting it wrong sizes your pools wrong.

Exit code 137 is not an OOM you can debug from Java. It's the kernel OOM-killer, and it leaves no heap dump and no stack trace. If you're seeing 137s, you have a native/RSS budgeting problem, not a heap problem — reach for Native Memory Tracking, not MAT.

Q24Should you call System.gc()?

No. It's a hint, typically triggering a Full GC — the single most expensive thing the JVM does — at a moment you chose arbitrarily and the JVM didn't. In a latency-sensitive service that's a self-inflicted pause.

It can be disabled outright with -XX:+DisableExplicitGC, which many production estates set precisely because a library somewhere calls it.

The nuance that shows depth — the one legitimate-ish caller is NIO's DirectByteBuffer cleanup path, which historically relied on System.gc() to reclaim off-heap buffers. If you set DisableExplicitGC, pair it with -XX:+ExplicitGCInvokesConcurrent so the request becomes a concurrent cycle instead of being silently dropped.

Q25What is false sharing, and have you ever hit it?

Two threads write to two different variables that happen to sit in the same 64-byte cache line. Nothing is logically shared, but the cache-coherence protocol invalidates the whole line on every write, so the cores ping-pong it and throughput collapses.

Fixes: pad the fields apart, or annotate with @jdk.internal.vm.annotation.Contended (needs -XX:-RestrictContended). In practice, use the JDK classes that already solve it: LongAdder over AtomicLong under high contention — it keeps per-thread striped cells on separate lines and sums on read.

Say the trade-off: "LongAdder is faster to increment but its sum() isn't atomic against concurrent updates. For a hit counter that's fine. For a wallet balance it isn't — there I want a single source of truth with proper transactional semantics, not a striped counter."

Q26Do virtual threads change anything about memory?

Yes, substantially — and it's a good thing to raise if the conversation reaches Java 21.

  • A platform thread reserves a fixed OS stack (~1 MB of virtual address space). That's why a few thousand threads is a practical ceiling.
  • A virtual thread's stack lives on the heap as a continuation, starts tiny, and grows and shrinks on demand. Millions are viable. The scheduler is a ForkJoinPool of carrier threads.
  • Consequence: thread pools stop being the right pattern for blocking I/O. Executors.newVirtualThreadPerTaskExecutor() replaces them; you no longer size a pool to protect the machine, so you move back-pressure to an explicit semaphore or rate limiter where it belongs.

Pinning is the detail to have ready: a virtual thread inside a synchronized block that blocks will pin its carrier thread, defeating the whole mechanism. Use ReentrantLock instead. (JDK 24 removes most of this limitation — worth saying you know it was addressed.) Also: don't put ThreadLocals on virtual threads — with millions of threads the memory cost is real. That's exactly what ScopedValue (Q12) is for.

These two topics are named explicitly in multiple public Entain India reports — collections and threads with the Tech Lead, multithreading again with the Architect. Q27Explain how HashMap works internally.

Array of buckets → hash the key → index → walk the bucket. Everything else is detail on top of that sentence.

  • Hashing — hash = h ^ (h >>> 16), spreading high bits into the low bits, because the index is (n - 1) & hash and n is a power of two (so only the low bits would otherwise matter).
  • Collisions — a linked list in the bucket. Since Java 8, a bucket with ≥ 8 entries converts to a red-black tree (given table size ≥ 64), taking worst case from O(n) to O(log n). It untreeifies below 6.
  • Resize — at size > capacity × loadFactor (default 0.75), capacity doubles and entries rehash. In Java 8 an entry either stays at index i or moves to i + oldCap, decided by one bit — no full recomputation.
  • Nulls — one null key (bucket 0), many null values.

The senior addition: "the treeification fix in Java 8 was a response to a real hash-collision DoS: an attacker sends crafted keys that all land in one bucket and every lookup degrades to a linear scan. That's a live concern anywhere you build a map keyed on user-supplied strings." At a betting company, that is a security answer as well as a data-structures answer.

Sizing: "if I know I'm inserting ~1000 entries I construct with new HashMap<>(1365) — capacity above n / 0.75 — to avoid two resizes and their rehashing cost."

The two things they're really probing:

  1. Why no nulls in ConcurrentHashMap? Because map.get(k) == null would be ambiguous — absent, or present-with-null? In a single-threaded map you disambiguate with containsKey; concurrently, the answer can change between the two calls. Doug Lea removed the ambiguity by banning null.
  2. Thread-safe methods ≠ thread-safe code. if (!map.containsKey(k)) map.put(k, v); is a race even on a ConcurrentHashMap. Use the atomic composites: putIfAbsent, computeIfAbsent, merge, compute.

Q29Fail-fast vs fail-safe iterators?

Fail-fast (ArrayList, HashMap) — the collection keeps a modCount; the iterator snapshots it and throws ConcurrentModificationException if it changes. It's a bug detector, explicitly best-effort — never write logic that depends on it firing.

Fail-safe (CopyOnWriteArrayList, ConcurrentHashMap) — iterates a snapshot or is weakly consistent: never throws, but may not reflect concurrent changes.

// throws CME
for (String s : list) if (s.isBlank()) list.remove(s);

// correct
list.removeIf(String::isBlank);
// or
Iterator<String> it = list.iterator();
while (it.hasNext()) if (it.next().isBlank()) it.remove();

CME is not only a multithreading error — the single-threaded for-each-and-remove above is the most common cause by far. Say that; many candidates assert it's a concurrency-only exception.

Q30ArrayList vs LinkedList — which do you actually use?

ArrayList, almost always. The textbook answer favours LinkedList for insertions; the real answer is that cache locality beats asymptotics at realistic sizes.

  • ArrayList — contiguous array. O(1) indexed access, O(n) mid-list insert/remove (but it's System.arraycopy, which is brutally fast and cache-friendly). Grows by ~1.5×.
  • LinkedList — doubly-linked nodes. O(1) insert/remove given the node, but O(n) to find it. Each node is a separate heap object with two extra pointers — poor locality and ~3× the memory overhead.

The honest answer: "I use ArrayList by default. LinkedList only earns its place when I'm genuinely using it as a Deque — constant-time add/remove at both ends — and even then ArrayDeque is usually faster because it's array-backed. I don't think I've deliberately chosen LinkedList in production."

Q32The equals/hashCode contract — state it and say what breaks.

  1. Equal objects must have equal hash codes.
  2. Unequal objects may collide — that's allowed, just slower.
  3. hashCode must be consistent while the object's equals-relevant state is unchanged.
  4. equals must be reflexive, symmetric, transitive, consistent, and x.equals(null) is false.

Break rule 1 and hash collections silently lose entries: you put an object and get returns null, because you're looking in the wrong bucket. Break rule 3 — by mutating a key after insertion — and the entry is unreachable and unremovable, which is a leak (Q11).

The symmetry trap with inheritance: if Sub.equals compares extra fields but Super.equals doesn't, then sup.equals(sub) is true while sub.equals(sup) is false — symmetry broken, and collections behave non-deterministically. That's why Joshua Bloch's guidance is favour composition over inheritance for value types, and why getClass() != o.getClass() is safer than instanceof here. Best modern answer: use a record — you get a correct equals, hashCode and toString generated for free.

Q33How do you create a thread, and why prefer an ExecutorService?

  • extends Thread — burns your one inheritance slot. Avoid.
  • implements Runnable — better; no return value, can't throw checked exceptions.
  • implements Callable<T> — returns a value, can throw. Submit to an executor, get a Future.
  • ExecutorService — the answer. Decouples task submission from execution policy, reuses threads (thread creation is expensive), bounds concurrency, and gives you lifecycle control.

Avoid Executors.newFixedThreadPool / newCachedThreadPool in production. Fixed pools use an unbounded LinkedBlockingQueue — under overload you queue until OOM instead of shedding load. Cached pools create unbounded threads. Construct ThreadPoolExecutor directly with a bounded queue, a named ThreadFactory (so thread dumps are readable), and an explicit RejectedExecutionHandler. Choosing CallerRunsPolicy gives you natural back-pressure: the submitting thread does the work, so it stops submitting.

If Java 21 is in play, add: "for blocking I/O I'd now reach for newVirtualThreadPerTaskExecutor() and move back-pressure to an explicit semaphore, because pool sizing stops being the limiter." (Q26.)

Q35What is a deadlock, and how do you prevent and detect one?

Four Coffman conditions, all required: mutual exclusion, hold-and-wait, no preemption, circular wait. Break any one and deadlock is impossible.

Prevention, in order of preference:

  1. Lock ordering — impose a global order (e.g. always lock the lower account ID first). Breaks circular wait. This is the answer for a money-transfer question.
  2. tryLock with a timeout — breaks hold-and-wait; back off and retry with jitter.
  3. Reduce lock scope, or remove the lock with an immutable or lock-free design.
  4. Never call unknown/foreign code while holding a lock — that's how you acquire a lock you didn't know about.

Detection: jstack <pid> or jcmd <pid> Thread.print — HotSpot prints "Found one Java-level deadlock" and names both threads and both monitors. JConsole's "Detect Deadlock" button does the same. Programmatically, ThreadMXBean.findDeadlockedThreads().

Name the neighbours: livelock (threads keep responding to each other and make no progress), starvation (a thread never gets the lock — which is what ReentrantLock's fairness flag addresses, at a throughput cost).

Q36CompletableFuture — why, and what are the traps?

Future.get() blocks and you can't compose or chain. CompletableFuture gives you a non-blocking pipeline.

CompletableFuture<Odds>   odds   = supplyAsync(() -> oddsClient.fetch(id), pool);
CompletableFuture<Limits> limits = supplyAsync(() -> limitsClient.fetch(user), pool);

odds.thenCombine(limits, BetQuote::of)
    .orTimeout(300, MILLISECONDS)
    .exceptionally(ex -> BetQuote.unavailable())
    .thenAccept(this::publish);
  • thenApply — transform. thenCompose — flatMap, when the function itself returns a future (use this to avoid CompletableFuture<CompletableFuture<T>>).
  • thenCombine — join two independent futures. allOf / anyOf — fan-in.
  • exceptionally / handle / whenComplete — error paths. orTimeout (Java 9+) — bound the wait.

Two traps worth naming. (1) Always pass your own executor. The default is the common ForkJoinPool, sized to CPU count and shared with parallel streams — put blocking I/O on it and you starve the whole JVM. (2) The non-Async variants may run on whichever thread completed the previous stage, which can be a Netty event loop. If the work is non-trivial, use the *Async variant with an explicit pool.

Q37How would you make a class immutable, and why bother?

  1. Class final (or all constructors private) — no subclass can break the invariant.
  2. All fields private final.
  3. No setters, no method that mutates state.
  4. Defensive-copy mutable fields on the way in and on the way out. This is the step candidates miss.

Why: inherently thread-safe with zero synchronisation; safe as a map key; safe to cache and share; no partially-constructed states; and the JMM guarantees correctly-constructed final fields are visible to other threads without synchronisation.

Modern answer: record (Java 16+) gives you final fields, a canonical constructor, equals/hashCode/toString. But a record is only shallowly immutable — a List component is still mutable, so you still copy in the compact constructor:

public record Bet(String id, BigDecimal stake, List<Selection> selections) {
    public Bet {
        selections = List.copyOf(selections);   // defensive copy
    }
}

Q38Checked vs unchecked exceptions — what's your position?

Checked (extends Exception) — compiler-enforced, for recoverable conditions the caller can plausibly act on. Unchecked (extends RuntimeException) — programming errors and unrecoverable conditions.

Have a position, don't recite the definition: "In practice I lean toward unchecked for service-layer code. Checked exceptions leak implementation detail up the call stack, they compose badly with lambdas and streams, and in real codebases they get caught-and-swallowed, which is worse than not having them. I use a small set of unchecked domain exceptions and handle them once at the boundary — a @RestControllerAdvice in Spring."

The trap question: "what if finally has a return?" It discards the exception or the earlier return value entirely — the exception is silently swallowed. Never return from finally. Related: with try-with-resources, if both the body and close() throw, the body's exception wins and the close exception is attached as suppressed (getSuppressed()) — which is exactly why try-with-resources beats a hand-written finally { close(); }.

8. Coding Concepts — Spring Boot, SQL, Kafka, Redis#

"Coding Concepts" on the invite most likely means the applied layer: how you build a service, not just how the language works. All four topics below appear in public Entain India reports. Parts 02 and 07 go deeper on Spring; this is the Entain cut.

Q39What does Spring Boot auto-configuration actually do?

@SpringBootApplication = @Configuration + @ComponentScan + @EnableAutoConfiguration.

Auto-configuration reads candidate configuration classes from META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (Boot 3; spring.factories in Boot 2), then applies each one conditionally: @ConditionalOnClass (is the library on the classpath?), @ConditionalOnMissingBean (have you already defined your own?), @ConditionalOnProperty.

The sentence that lands it: "@ConditionalOnMissingBean is the key to the whole design — auto-config always backs off if you've defined the bean yourself. That's why Boot feels like sensible defaults rather than magic you have to fight."

Know the debugging move: run with --debug and Boot prints the Conditions Evaluation Report — every auto-config that matched, and every one that didn't, with the reason. Saying that is more convincing than any definition.

Q40Constructor vs field injection?

Constructor injection, always. Reasons, in order of weight:

  1. Dependencies can be final → the object is immutable and fully initialised at construction.
  2. You can instantiate it in a unit test with new, no Spring context, no reflection.
  3. A constructor with eight parameters looks wrong — the pain is a design signal. Field injection hides it.
  4. No NullPointerException from a half-wired bean.
  5. Circular dependencies fail fast at startup rather than being silently resolved.

Since Spring 4.3, a single-constructor class needs no @Autowired at all — with Lombok's @RequiredArgsConstructor it's one annotation on the class.

If asked how to break a genuine circular dependency: @Lazy works but is a plaster. The real fix is to extract the shared behaviour into a third bean, or publish an event. Note Boot 2.6+ disallows circular references by default — that change was deliberate.

Q41How does @Transactional work, and where does it silently not work?

Spring creates a proxy (JDK dynamic proxy for interfaces, CGLIB subclass otherwise). The proxy opens a transaction before the method and commits or rolls back after.

The three failures they're fishing for:

  1. Self-invocation. this.otherMethod() inside the same bean bypasses the proxy entirely, so @Transactional on otherMethod does nothing. Fix: move it to another bean, or self-inject.
  2. Non-public methods. Ignored by the default proxy mode. No error, no transaction.
  3. Rollback rules. By default Spring rolls back on RuntimeException and Error — not on checked exceptions. If you throw a checked exception expecting a rollback, you commit instead. Use @Transactional(rollbackFor = Exception.class).

Know the propagation values: REQUIRED (default — join or start), REQUIRES_NEW (suspend the outer, start a genuinely independent one — the right choice for an audit record that must survive a business rollback), NESTED (savepoint), MANDATORY, SUPPORTS, NEVER.

If the conversation turns to money — which at Entain it might — say: "for a wallet debit I'd want the isolation level to be explicit rather than inherited from the database default, and I'd lean on optimistic locking with @Version plus a retry, because pessimistic row locks on a hot account row become a throughput ceiling under peak load."

Q42What is the N+1 problem and how do you fix it?

You load N parents with one query, then touching a lazy association fires one query per parent — N+1 round trips. It passes every test with 3 rows and destroys production with 10,000.

Fixes, in order:

  • JOIN FETCH in JPQL — one query, one join.
  • @EntityGraph on the repository method — declarative, keeps the derived query.
  • @BatchSize(size = 25) — turns N queries into N/25 IN (…) queries. Good when a join would produce a cartesian product.
  • A projection or DTO query — fetch only the columns you need.

How you detect it is the better half of the answer: "I turn on spring.jpa.show-sql or, better, run datasource-proxy or Hibernate statistics in tests and assert on query count. Reading SQL logs by eye doesn't scale; a test that fails when a change adds a query does." That's a senior answer to a mid-level question.

Beware the pair-trap: JOIN FETCH on two collections throws MultipleBagFetchException (cartesian product). Fix with Set, or fetch one collection and @BatchSize the other.

Q43Write a SQL query to find the second-highest value — and then the top N per group.

Reported Entain rounds ask SQL live. Have both shapes ready.

-- Second highest stake, null-safe, handles ties
SELECT MAX(stake) FROM bets
WHERE stake < (SELECT MAX(stake) FROM bets);

-- Or with a window function (say this one — it generalises to Nth)
SELECT stake FROM (
  SELECT stake, DENSE_RANK() OVER (ORDER BY stake DESC) AS rnk
  FROM bets
) t WHERE rnk = 2;

-- Top 3 bets per customer
SELECT customer_id, bet_id, stake
FROM (
  SELECT customer_id, bet_id, stake,
         ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY stake DESC) AS rn
  FROM bets
) t
WHERE rn <= 3;

Know the difference cold, because it's the follow-up: ROW_NUMBER = 1,2,3,4 (arbitrary tie-break); RANK = 1,2,2,4 (gaps); DENSE_RANK = 1,2,2,3 (no gaps). For "second highest distinct value" you want DENSE_RANK.

Other SQL they may ask: find duplicates (GROUP BY … HAVING COUNT(*) > 1), delete duplicates keeping one (ROW_NUMBER in a CTE), and the difference between WHERE and HAVING (row filter before aggregation vs group filter after). And know why SELECT * plus a function on an indexed column kills the index — WHERE YEAR(created_at) = 2026 can't use the index; WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01' can.

Q44Explain database indexes — when do they hurt?

A B+ tree keyed on the indexed columns; leaves are sorted and linked, so equality and range scans are both fast. A clustered index is the table's physical order (InnoDB's primary key); a secondary index stores the PK and needs a second lookup unless the index covers every column the query needs.

When they hurt:

  • Every write must update every index — heavy-write tables pay for each one.
  • Low-cardinality columns (a boolean, a status with 3 values) rarely benefit; the planner often prefers a table scan anyway.
  • They consume memory and disk, and bloat the buffer pool.

Composite index order is the question that separates people. An index on (customer_id, created_at) serves WHERE customer_id = ? and WHERE customer_id = ? AND created_at > ? — but not WHERE created_at > ? alone. Leftmost-prefix rule. Put the equality column first, the range column last.

Always finish with: "and I'd confirm with EXPLAIN / EXPLAIN ANALYZE rather than reasoning about it — the planner's row estimates are what actually decide."

Q45Kafka — partitions, consumer groups, ordering and delivery guarantees.

  • A topic is split into partitions; a partition is an ordered, append-only log. Ordering is guaranteed per partition, never across a topic.
  • The partition key decides placement (hash(key) % partitions). Key by customerId and all of one customer's events are ordered — that's how you get ordering where it matters.
  • In a consumer group, each partition is consumed by exactly one member. Partition count is your parallelism ceiling — more consumers than partitions leaves some idle.
  • Delivery: at-most-once (commit before processing), at-least-once (commit after — the sane default), exactly-once (idempotent producer + transactions, at a throughput cost).

The senior line: "at-least-once plus an idempotent consumer is what I'd actually build. Exactly-once in Kafka only holds within Kafka — the moment you write to an external database or call a payment API, the guarantee ends. Idempotency keys on the consumer side are the real answer." At a betting company, "process this settlement exactly once" is the whole problem, so this lands well.

Have answers for: consumer lag (and how you alert on it), rebalancing storms (max.poll.interval.ms too low for slow processing), and what you do with a poison message (retry topic + DLT, with attempt count in a header).

Q46Redis — what do you use it for, and what are the pitfalls?

Uses: cache-aside, distributed session store, distributed lock, rate limiter (token bucket via INCR + EXPIRE, or a Lua script for atomicity), leaderboards (sorted sets — a natural fit for betting), pub/sub, and Streams as a lightweight queue.

Caching patterns: cache-aside (read-through by hand — the default), write-through, write-behind. Know the failure modes:

  • Cache stampede / thundering herd — a hot key expires and a thousand requests hit the DB at once. Fix: a per-key lock so one caller refreshes, or probabilistic early expiry.
  • Cache penetration — repeated lookups for a key that doesn't exist. Fix: cache the negative result briefly, or a Bloom filter.
  • Cache avalanche — many keys expiring at once. Fix: jitter the TTLs.

On distributed locks, have the honest opinion: "a naive SETNX lock isn't safe — you need a unique token and a Lua script to release, so you don't delete someone else's lock after your TTL expired. Redlock is contested; Martin Kleppmann's critique is that it doesn't survive GC pauses and clock skew. So I use a Redis lock for efficiency — stopping duplicate work — and never for correctness. Correctness goes in the database with a unique constraint or a conditional update." That answer is worth a lot in a round that reportedly asks about Redis.

Q47How do you make an API idempotent?

Highly likely at a betting company: "the customer's place-bet request timed out and the app retried. How do you avoid taking the stake twice?"

  1. Client generates an idempotency key (a UUID) per logical operation and sends it as a header. Retries reuse the same key.
  2. Server stores the key in a table with a unique constraint, alongside the request hash and the eventual response.
  3. First request: insert the key, process, store the response. Duplicate: the insert violates the constraint → return the stored response, don't re-execute.
  4. Handle the in-flight case (key present, response not yet stored) with a 409 or a short wait; expire keys after 24h.
  5. Reject a reused key with a different request body — that's a client bug you want surfaced, not silently absorbed.

Tie it back to HTTP semantics: GET, PUT and DELETE are idempotent by definition; POST is not, which is exactly why it needs the key. And say where the uniqueness lives: in the database, not in Redis — see Q46.

Q48How do you keep a service resilient when a downstream dependency is slow?

  • Timeouts on everything. A missing timeout is how one slow dependency takes down every thread in your pool. Connect timeout and read timeout.
  • Circuit breaker (Resilience4j) — after a failure-rate threshold, open the circuit and fail fast; half-open to probe recovery. It protects you from waiting and them from a thundering herd.
  • Retry with exponential backoff and jitter — and only on idempotent operations and retryable errors. Retrying a non-idempotent POST without an idempotency key is how you double-charge someone.
  • Bulkhead — separate pools per dependency, so one slow integration can't consume all the threads.
  • Fallback — a cached value, a degraded response, or an honest error. Decide deliberately which is acceptable.

The point to make: "retry and circuit breaker fight each other if you order them wrong — retrying inside the breaker inflates the failure count and trips it early. In Resilience4j the sane order is Retry wrapping CircuitBreaker wrapping the call, so the breaker sees real calls and the retry respects an open circuit."

9. Problem Solving — the coding bank#

Reported Entain India coding is easy-to-medium, weighted toward strings, arrays and example programs, with the HackerRank stage described as harder. Several reports stress that they care more about how you think than which technology you know. So narrate.

9.2 Arrays and maps

Q54Two Sum — return indices of the pair summing to target.

static int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> seen = new HashMap<>();   // value -> index
    for (int i = 0; i < nums.length; i++) {
        Integer j = seen.get(target - nums[i]);
        if (j != null) return new int[]{j, i};
        seen.put(nums[i], i);                        // put AFTER the check
    }
    return new int[0];
}

Putting before checking breaks target = 2×nums[i] by matching an element with itself. Also: this is the archetype for "I traded O(n) space for O(n) time instead of O(n²)" — say that sentence; it's the whole lesson of the problem and it generalises to half the bank.

Q55Find duplicates in an array; find the missing number in 1..n.

// Duplicates
Set<Integer> seen = new HashSet<>(), dupes = new HashSet<>();
for (int n : nums) if (!seen.add(n)) dupes.add(n);     // add() returns false if present

// Missing number in 1..n — the O(1) space answer
static int missing(int[] nums, int n) {
    long expected = (long) n * (n + 1) / 2;            // long guards overflow
    long actual = 0;
    for (int v : nums) actual += v;
    return (int) (expected - actual);
}

Two things to volunteer: Set.add returning a boolean is the idiomatic dup check (no contains-then-add), and the XOR variant of "missing number" avoids overflow entirely — XOR all values with all indices and the survivors cancel. Mentioning overflow unprompted is a real signal at a company that handles money.

Q56Maximum subarray sum (Kadane's).

static int maxSubArray(int[] a) {
    int best = a[0], current = a[0];
    for (int i = 1; i < a.length; i++) {
        current = Math.max(a[i], current + a[i]);   // extend, or start fresh here
        best = Math.max(best, current);
    }
    return best;   // O(n) time, O(1) space
}

Explain the invariant in one line — "current is the best sum of a subarray ending at i; if the running sum is worse than the element alone, start fresh" — and note it handles all-negative arrays correctly because best starts at a[0], not 0. That edge case is the usual bug.

9.3 Concurrency, written live

Q58Producer–consumer with a bounded buffer.

Reported at Entain in two separate rounds under "multithreading". Write the simple version first and say why.

// The answer you give first
BlockingQueue<Bet> queue = new ArrayBlockingQueue<>(1000);

// producer
queue.put(bet);          // blocks when full -> back-pressure for free
// consumer
Bet bet = queue.take();  // blocks when empty

Then, if they ask you to hand-roll it:

private final Queue<Bet> q = new ArrayDeque<>();
private final int capacity;

public synchronized void put(Bet b) throws InterruptedException {
    while (q.size() == capacity) wait();   // while, never if
    q.add(b);
    notifyAll();
}

public synchronized Bet take() throws InterruptedException {
    while (q.isEmpty()) wait();
    Bet b = q.poll();
    notifyAll();
    return b;
}

Three things they are specifically checking. (1) while not if — because of spurious wakeups, and because another thread can win the lock between your notify and your wake. (2) notifyAll not notify — with mixed producers and consumers, notify can wake the wrong kind and deadlock. (3) wait() must be called holding the monitor, and it releases it while waiting — sleep() doesn't. Getting all three right is the whole question.

Finish with the judgement call: "in production I'd use ArrayBlockingQueue — this is exactly the thing you don't hand-roll. And the bound matters: an unbounded queue just moves an overload problem into a slower OOM."

Q59Implement a thread-safe LRU cache.

class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LruCache(int capacity) {
        super(16, 0.75f, true);        // true = ACCESS order, the whole trick
        this.capacity = capacity;
    }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}

synchronizedMap serialises every operation — one lock for the whole cache. Say so, and say the production answer: "Caffeine. It gives me concurrent access, size and time eviction, refresh-ahead and hit-rate stats. A hand-rolled LRU in production is a maintenance liability, and a naive ConcurrentHashMap + LRU list isn't actually thread-safe anyway because the two structures can't be updated atomically."

Q60Print odd and even numbers alternately with two threads.

A perennial Indian-market interview favourite. Know it cold.

class Alternator {
    private int n = 1;
    private final int max;
    Alternator(int max) { this.max = max; }

    synchronized void print(boolean odd) throws InterruptedException {
        while (n <= max) {
            while (n % 2 == (odd ? 0 : 1)) {       // not my turn
                if (n > max) return;
                wait();
            }
            if (n > max) return;
            System.out.println(Thread.currentThread().getName() + ": " + n++);
            notifyAll();
        }
    }
}

If they let you choose the mechanism, Semaphore is cleaner and worth showing: two semaphores, one permit initially on the odd one; each thread acquires its own and releases the other's. Say "this is a turn-taking problem, so a pair of semaphores expresses it more directly than wait/notify" — the framing is the mark, not the code.

Q61Transfer money between two accounts without deadlocking.

The most Entain-flavoured concurrency question there is. Two threads, transfer(A→B) and transfer(B→A), locking in argument order, deadlock immediately.

void transfer(Account from, Account to, BigDecimal amount) {
    Account first  = from.id().compareTo(to.id()) < 0 ? from : to;
    Account second = (first == from) ? to : from;     // GLOBAL LOCK ORDER
    synchronized (first) {
        synchronized (second) {
            if (from.balance().compareTo(amount) < 0)
                throw new InsufficientFundsException(from.id());
            from.debit(amount);
            to.credit(amount);
        }
    }
}

Two edges to raise before they do: self-transfer (from == to — guard it, or you double-count), and equal IDs if the ordering key isn't unique (fall back to System.identityHashCode, with a tie-breaker lock for the rare collision).

Then reframe it, and this is what separates you from an SDE I: "in a real wallet I wouldn't be holding JVM monitors at all — there's more than one instance of the service, so an in-process lock guarantees nothing. The ordering would be enforced in the database, with the transfer in one transaction, an optimistic @Version check and a retry, and the ledger written as immutable double-entry rows rather than a mutable balance column. The balance becomes a projection you can always rebuild and audit."

Q62Longest substring without repeating characters.

static int longestUnique(String s) {
    Map<Character, Integer> last = new HashMap<>();
    int best = 0, start = 0;
    for (int i = 0; i < s.length(); i++) {
        Integer prev = last.get(s.charAt(i));
        if (prev != null && prev >= start) start = prev + 1;  // the guard matters
        last.put(s.charAt(i), i);
        best = Math.max(best, i - start + 1);
    }
    return best;   // O(n) time, O(k) space
}

Name the technique — sliding window — before you write it. prev >= start is the classic bug: without it, a repeat from before the current window drags start backwards.

Q63Merge overlapping intervals.

static List<int[]> merge(int[][] intervals) {
    Arrays.sort(intervals, Comparator.comparingInt(a -> a[0]));
    List<int[]> out = new ArrayList<>();
    for (int[] iv : intervals) {
        if (!out.isEmpty() && iv[0] <= out.get(out.size() - 1)[1])
            out.get(out.size() - 1)[1] = Math.max(out.get(out.size() - 1)[1], iv[1]);
        else
            out.add(iv.clone());
    }
    return out;   // O(n log n), dominated by the sort
}

The Math.max on the end is the bug people ship — a fully-contained interval would otherwise shrink the merged one. And this has a natural betting framing: merging a customer's overlapping self-exclusion or session windows.

Q64Top K frequent elements.

static List<String> topK(List<String> items, int k) {
    Map<String, Long> freq = items.stream()
        .collect(Collectors.groupingBy(x -> x, Collectors.counting()));

    PriorityQueue<Map.Entry<String, Long>> heap =
        new PriorityQueue<>(Map.Entry.comparingByValue());   // MIN-heap

    for (var e : freq.entrySet()) {
        heap.offer(e);
        if (heap.size() > k) heap.poll();     // drop the smallest
    }
    return heap.stream().map(Map.Entry::getKey).toList();
}

Say why a min-heap of size k, not a max-heap: it gives O(n log k) instead of O(n log n), and O(k) space rather than O(n). "Most-backed selections in the last hour" is the same problem with a time window — a reasonable follow-up at Entain, and the answer there is a bucketed count with sliding expiry, or Redis sorted sets.

Q65Given a stream of bets, detect a customer exceeding a limit in any 60-second window.

A plausible Entain-flavoured "problem solving" question. It's a sliding-window rate limiter wearing a domain costume — recognise it and say so.

class WindowedLimiter {
    private final Map<String, Deque<Long>> events = new ConcurrentHashMap<>();
    private final int limit; private final long windowMs;

    boolean allow(String customerId, long nowMs) {
        Deque<Long> d = events.computeIfAbsent(customerId, k -> new ArrayDeque<>());
        synchronized (d) {                       // per-customer lock, not global
            while (!d.isEmpty() && d.peekFirst() <= nowMs - windowMs)
                d.pollFirst();                   // evict what left the window
            if (d.size() >= limit) return false;
            d.addLast(nowMs);
            return true;
        }
    }
}

Then raise the two problems yourself, because that's the actual test. (1) Unbounded memory — the outer map grows one deque per customer forever; needs expiry or a bounded cache. (2) It's per-instance — with three replicas a customer gets 3× the limit, so the counter has to move to Redis (a sorted set of timestamps with ZREMRANGEBYSCORE, or a token bucket in a Lua script for atomicity).

Then name the trade-off between algorithms: fixed window is cheapest but allows a 2× burst across the boundary; sliding log is exact but stores every timestamp; token bucket is the usual production choice — O(1) memory per key, allows a controlled burst. Knowing when a domain problem is a standard problem is the skill they're testing.

10. If design comes up#

Q66Design a distributed queue.

Clarify first: ordering guarantee? delivery guarantee? durability? throughput? consumers competing or broadcast?

Core design:

  • Partitioned append-only log, exactly as Kafka does it. Partition by key so per-key ordering holds; total ordering across partitions is deliberately not offered, because it would serialise everything.
  • Replication — each partition has a leader and N followers; a write is acknowledged when a quorum (or the in-sync replica set) has it. Leader election on failure.
  • Consumer offsets stored durably, committed after processing → at-least-once.
  • Visibility timeout (the SQS model) if you want competing consumers on a single queue rather than partition ownership: a message is hidden while being processed, and reappears if not acknowledged in time.
  • Retention — time- or size-based; consumers can replay, which is the log's superpower over a traditional queue.
  • Dead-letter queue after N failed attempts, so one poison message can't block a partition forever.

Say the three things explicitly — ordering is per-partition only; delivery is at-least-once so consumers must be idempotent; and partition count bounds consumer parallelism and is painful to change later, so over-provision it. Naming those is what makes it a design answer rather than a description of Kafka.

Q67Design the bet placement flow.

Part 03 §5E is the full version. The four-minute spoken skeleton:

  1. Request → API gateway (auth, rate limit) → Bet Service.
  2. Validate: market still open, odds still valid (reject or re-quote if they moved), selection combination legal, customer eligible — and the responsible-gambling checks: deposit limits, self-exclusion, affordability. Say this unprompted; it is a real part of the domain.
  3. Reserve funds in the wallet — a single transaction, optimistic locking with @Version, idempotency key on the request (Q47) so a client retry can't double-stake.
  4. Persist the bet and emit a BetPlaced event (transactional outbox, so the DB write and the publish can't diverge).
  5. Downstream consumers: risk/liability engine, CRM, reporting, settlement — all decoupled and asynchronous.
  6. Settlement on result: an event-driven consumer credits winnings, idempotently, keyed on (betId, resultVersion).

The two hard parts to name, because naming them is the senior move: (1) odds change between quote and placement — you need a version on the price and an explicit accept-or-reject policy; (2) settlement must be exactly-once from the customer's perspective, which you get from at-least-once delivery plus an idempotent consumer with a uniqueness constraint in the ledger, not from a broker's exactly-once flag (Q45).

Q68How do you keep a live odds feed fast for a million clients?

  • Push, don't poll — WebSocket, or SSE if it's one-directional. Polling a million clients is a self-inflicted DDoS.
  • Fan-out — a pub/sub layer (Redis pub/sub, Kafka, or a purpose-built gateway tier) with clients subscribed per market, so an odds change touches only subscribers of that market.
  • Send deltas, not snapshots, with a sequence number so a client can detect a gap and request a resync.
  • Conflate — if odds change five times in 200 ms, send the latest, not all five. Slow clients get the current state, not a backlog.
  • Edge — CDN and regional gateways for connection termination; keep the hot path in memory.
  • Back-pressure — bound the per-connection outbound buffer and drop the slow consumer rather than letting it grow your heap (tie it back to §6 — this is exactly how a feed service OOMs).

Have the honest caveat ready: "the consistency model matters more than the latency number. A customer must never place a bet at a price that no longer exists, so the authoritative check happens server-side at placement (Q67) — the feed is an optimisation for the UI, not the source of truth."

I'd rather be solving harder problems at SDE II here than easier ones with a bigger title elsewhere — and I'd expect the level to follow the work."

The real risk isn't the title — it's how you answer the technical questions. At 5+ years you can accidentally over-answer: a rapid-fire collections question gets a four-minute architectural response and the interviewer reads it as poor calibration. Answer at the altitude of the question. Lead line, one layer of depth, then stop and offer more. That discipline is the seniority signal — more than any amount of extra content.

And the flip side, which is your actual advantage: when a question does open up — a leak, a deadlock, a design trade-off — you have production scars and an SDE II candidate doesn't. That's where you spend your depth. §6 Q22, §7 Q35 and §9 Q61 are the three most likely doors.

14.1 Collections — the most likely topic

Q75What is a HashMap?

Your answer — "It stores key–value pairs. You give it a key, it gives you back the value, very fast. Inside, it's an array of buckets. It takes the key, calculates a hash number from it, and that number decides which bucket to use."

↳ Level 1 — "What happens if two keys land in the same bucket?"

"That's called a collision. Both entries go in the same bucket, stored as a linked list. When you look one up, Java walks the list and uses equals() to find the right one.

Since Java 8, if one bucket gets too crowded — 8 or more entries — Java converts that list into a tree. A list takes longer and longer to search as it grows. A tree stays fast."

↳ Level 2 — "Why did they bother adding the tree? A list works."

"Because of an attack. If someone knows your keys are user input, they can deliberately send thousands of keys that all hash to the same bucket. Now every lookup has to walk a huge list, your CPU goes to 100%, and the server stops responding. That's a denial-of-service attack.

The tree puts a floor under the worst case. Instead of getting slower and slower in a straight line, it stays reasonable."

If they push further: "the other thing that matters is resizing. When the map gets about 75% full, it doubles in size and moves everything. That's expensive. So if I know I'm going to store 1000 items, I create the map with a bigger starting size to avoid the resize."

Q76HashMap is not thread-safe. What do you use instead?

Your answer — "ConcurrentHashMap. It's built for multiple threads. The old option was Hashtable, but that locks the entire map for every single operation, so threads queue up behind each other. ConcurrentHashMap only locks the one bucket being touched, so other threads can keep working."

↳ Level 1 — "So if I use ConcurrentHashMap, my code is thread-safe?"

"No — and this is the trap. Each individual method is safe. But if I combine two methods, there's a gap in between where another thread can slip in.

For example: check if the key exists, and if not, add it. Two threads can both check at the same time, both see 'not there', and both add. One overwrites the other.

The fix is to use the methods that do both steps in one go — putIfAbsent, or computeIfAbsent. One operation, no gap."

↳ Level 2 — "Why can't you put null in a ConcurrentHashMap?"

"Because the answer would be ambiguous. If get(key) returns null, it could mean two things: the key isn't there, or the key is there and its value is null.

In a normal HashMap you can tell the difference by calling containsKey. But with multiple threads, the answer can change between your two calls — so you still don't know. They removed null entirely rather than leave you with a question you can't answer."

Q77ArrayList or LinkedList — which do you use?

Your answer — "ArrayList, nearly always. It's a plain array underneath. Getting item number 500 is instant. LinkedList is a chain of boxes, each pointing to the next — to reach item 500 you have to walk through 499 boxes first."

↳ Level 1 — "But the textbook says LinkedList is faster for inserting in the middle. Isn't it?"

"On paper, yes. In real life, usually no.

To insert in the middle of a LinkedList, you first have to find the middle — and that means walking the chain. The insert itself is fast, but the walk isn't.

ArrayList does have to shift items along. But it does that with a bulk memory copy, which processors are extremely good at. It's also all in one continuous block of memory, so the CPU cache works well. LinkedList scatters boxes all over memory, and every hop is a possible cache miss."

↳ Level 2 — "Is there any case where you'd pick LinkedList?"

"Honestly, almost never. If I need to add and remove from both ends — like a queue — I'd use ArrayDeque, not LinkedList. ArrayDeque does the same job and is faster, because it's array-based again.

I don't think I've ever deliberately chosen LinkedList in production code."

That last line is a good answer. Saying "the textbook answer is X but I've never actually needed it" shows real experience, not memorised theory.

Q78What's the contract between equals() and hashCode()?

Your answer — "If two objects are equal, they must return the same hash code. The reverse isn't required — two different objects can share a hash code, that's just a collision and it's allowed."

↳ Level 1 — "What breaks if I override equals but forget hashCode?"

"HashMap stops working, quietly.

You put an object in. Later you look it up with an equal object. But because the hash codes differ, the map looks in the wrong bucket, finds nothing, and returns null. Your object is in there — you just can't ever reach it.

Nothing throws an exception. It just silently returns the wrong answer, which is worse."

↳ Level 2 — "What if I change a field on an object after putting it in a HashMap?"

"Same problem, and now it's also a memory leak.

The object went into bucket 5 based on its original hash. You changed a field, so now it hashes to bucket 9. The map looks in bucket 9 and finds nothing. But the object is still sitting in bucket 5, holding memory, and you can't get it out — you can't even remove it, because remove() looks in bucket 9 too.

That's why keys should be immutable. It's why String and Integer make such good keys."

Easy win: "these days I'd just use a record. Java generates a correct equals, hashCode and toString for me, so there's nothing to get wrong."

Q79Why is String immutable?

Your answer — "Once you create a String, you can't change it. Any method that looks like it changes a String actually returns a brand new one."

↳ Level 1 — "Why did they design it that way?"

"Four reasons, and they all matter:

  • Safety. Strings are used for filenames, database URLs, usernames. If someone could change a String after you'd checked it was safe, they could check it, then change it.
  • Threads. If nothing can change, nothing can go wrong when many threads read it at once. No locking needed.
  • Caching the hash. Because it can never change, String calculates its hash code once and remembers it. That makes Strings very fast as HashMap keys.
  • Sharing. Java keeps a pool of Strings and reuses them. That's only safe if nobody can modify them.

↳ Level 2 — "So what do you use when you need to build a string in a loop?"

"StringBuilder. If I use + inside a loop, every single pass creates a whole new String and throws the old one away. With 10,000 items that's 10,000 wasted objects and it gets slower as the string grows.

StringBuilder keeps one buffer and appends to it.

Worth adding: outside a loop, + is fine — the compiler quietly turns it into a StringBuilder for you. It's specifically loops where it hurts, because the compiler can't do that across iterations."

14.2 Memory — your strongest card

Q80What's the difference between stack and heap?

Your answer — "The heap is where objects live. Every time you write new, that object goes on the heap, and it's shared by all threads.

The stack is per-thread. Each thread has its own. It holds local variables and keeps track of which method called which. When a method finishes, its part of the stack is thrown away automatically."

↳ Level 1 — "If I write Point p = new Point(), where does p live?"

"Split across both. The Point object itself is on the heap. The variable p — which is just an address pointing at that object — is on the stack.

Think of the heap as a warehouse and the stack as a sticky note with the shelf number written on it."

↳ Level 2 — "Are objects always on the heap?"

"By the rules of the language, yes. In the running machine, not always.

The JIT compiler does something called escape analysis. It checks whether an object can ever be seen outside the method that made it. If it can't, the JIT may skip creating the object entirely and just keep its fields in CPU registers.

That's why I don't usually try to hand-optimise away small short-lived objects — the JIT often does it for me. I'd rather write clear code and let a profiler tell me where it actually hurts."

That last paragraph is a strong finish. It says: I know the deep detail, and I know when not to act on it.

Q81How does garbage collection work?

Your answer — "Java automatically deletes objects you're no longer using. It doesn't count references. Instead it starts from a set of known starting points, called GC roots, and follows every link it can. Anything it can reach is kept. Anything it can't reach is deleted."

↳ Level 1 — "What counts as a GC root?"

"Things that are definitely alive:

  • Local variables in any running method
  • static fields
  • Threads that are currently running
  • Objects being locked right now

Everything else is only alive if something reachable points to it."

↳ Level 2 — "Why reachability and not simple reference counting?"

"Because counting can't handle circles.

Imagine object A points to B, and B points back to A. Nothing else points to either. Their counts are both 1, so a counting collector would keep them forever — even though nobody can reach them.

Reachability just asks 'can I get there from a root?' The answer is no, so both get collected. That's why a parent–child object graph isn't a leak in Java."

Then say this — it sets up every leak question: "which means a memory leak in Java is never about forgetting to free something. It's about accidentally keeping something reachable."

Q82Can you have a memory leak in Java?

Your answer — "Yes. Not the C kind where you forget to free memory. In Java it's when you accidentally hold on to something you've finished with. The GC sees a live reference, so it correctly refuses to delete it. The GC is working fine — you just told it the wrong thing."

↳ Level 1 — "Give me a real example."

"The classic one is a static Map used as a cache with nothing ever removing entries. Statics live for the whole life of the application, so everything in that map lives forever too. It grows until you run out of memory.

Others I've seen: registering a listener and never unregistering it; not closing streams or connections; and ThreadLocal in a thread pool."

↳ Level 2 — "Why is ThreadLocal a problem in a thread pool?"

"Because pool threads never die — they get reused for the next request.

Each thread holds a map of its ThreadLocal values, and those values are held strongly. So whatever I stored stays attached to that thread after my request is finished, and the next request gets the same thread.

That's a leak, and in a multi-user system it's worse than a leak — request B can read request A's data. That's a security bug.

The fix is to always call remove() in a finally block. Not set(null) — that leaves an empty entry behind. remove() deletes it properly."

Q83Your app throws OutOfMemoryError in production. What do you do?

Your answer — "First I stop the bleeding — is it one server or all of them, and did a recent deploy cause it? If so, roll back. Customers first, root cause second."

↳ Level 1 — "OK, you've stabilised it. Now how do you find the cause?"

"Three steps:

  1. Read the error message. 'Java heap space' means normal objects. 'Metaspace' means too many classes loaded. 'Unable to create new native thread' means too many threads. The message already narrows it down.
  2. Look at the GC log. I want one specific number: how full is the old generation right after each full garbage collection. If it goes up and comes back down, that's healthy — just busy. If it keeps creeping up and never comes back down, that's a leak.
  3. Take a heap dump and open it in Eclipse MAT. It shows what's holding the most memory and, more importantly, what is keeping it alive. That chain of references is the bug."

↳ Level 2 — "How do you know whether it's a leak or you just need more memory?"

"That one number from step 2 — old generation usage after a full GC.

If it returns to roughly the same baseline every time, memory is being reclaimed properly. The app just genuinely needs more room, so I increase the heap.

If the baseline climbs a little higher every cycle and never comes back, something is being retained. Adding memory won't fix that — it just buys time and makes the eventual pause longer.

The fixes are opposite, so getting this right first matters."

Great closing line: "and I always run with -XX:+HeapDumpOnOutOfMemoryError turned on. An OOM you didn't capture a dump for is an OOM you get to have twice."

Q84What is the young generation and old generation?

Your answer — "The heap is split in two. New objects go in the young generation. Objects that survive long enough get moved to the old generation."

↳ Level 1 — "Why split it at all?"

"Because most objects die almost immediately. Think of a method that creates a few temporary objects and returns — they're garbage within microseconds.

So instead of scanning the entire heap every time, Java scans just the young part, very often. That part is small and almost everything in it is dead, so cleaning it is cheap.

The key insight: the collector copies out the few survivors and wipes the rest in one go. Dead objects cost nothing to collect. So if 98% of it is garbage, the work is proportional to the 2%."

↳ Level 2 — "What's premature promotion?"

"When objects get moved to the old generation before they were ready to.

Objects normally bounce around the young area a few times before being promoted. But if the young area is too small, there's no room to bounce, so they get pushed into old early.

The problem is that the old generation is only cleaned by a full garbage collection, which is slow and pauses the whole application. So you end up doing expensive cleanups for objects that would have died cheaply on their own.

The symptom is the old generation growing steadily even though the load is steady. It looks like a leak but it's actually a sizing problem."

14.3 Threads — asked in two separate rounds

Q85How do you create a thread in Java?

Your answer — "Three ways. Extend Thread, implement Runnable, or implement Callable. But in real code I don't create threads directly — I use an ExecutorService and give it tasks."

↳ Level 1 — "Why not just create threads?"

"Creating a thread is expensive, and each one reserves about a megabyte of memory.

If I create a thread per request and traffic spikes, I create thousands of threads, run out of memory, and the server dies right when it's busiest.

A pool reuses a fixed set of threads. If more work arrives than the pool can handle, it queues — which is much better than falling over."

↳ Level 2 — "Which pool would you create?"

"Not the convenience ones. Executors.newFixedThreadPool looks safe, but its queue is unlimited. So under heavy load you don't reject anything — you just queue forever until you run out of memory. You've turned a fast failure into a slow one.

And newCachedThreadPool creates unlimited threads, which is worse.

So I build a ThreadPoolExecutor myself with a bounded queue, and I decide what happens when it's full. Usually CallerRunsPolicy — the thread that submitted the work has to do it itself. That naturally slows down whoever is flooding you.

I also give threads proper names, so when I read a thread dump at 2am I can tell what they are."

Q86What does volatile do?

Your answer — "It guarantees that when one thread writes a variable, other threads see the new value. Without it, each CPU core can cache its own copy, and a thread might keep reading a stale value forever."

↳ Level 1 — "So can I use volatile for a counter?"

"No, and this is the most common mistake.

count++ looks like one action but it's actually three: read the value, add one, write it back.

Two threads can both read 5, both add one, and both write 6. You did two increments and got one. volatile doesn't help, because each individual read and write was fine — the problem is the gap between them.

For a counter I'd use AtomicInteger, which does all three steps as one indivisible operation."

↳ Level 2 — "When would you use volatile then?"

"When one thread writes and others only read. A simple flag is the classic case:

private volatile boolean running = true;

public void stop() { running = false; }        // one thread writes
public void run()  { while (running) { … } }   // another reads

Without volatile, the loop might never see the change and run forever.

The rule I use: volatile for visibility, atomic or a lock for counting."

Q87What is a deadlock?

Your answer — "Two threads each holding something the other needs, and neither will let go. Thread A holds lock 1 and wants lock 2. Thread B holds lock 2 and wants lock 1. Both wait forever."

↳ Level 1 — "How do you prevent it?"

"The simplest and most reliable way is always lock in the same order.

If every thread in the system agrees to take lock 1 before lock 2 — always, no exceptions — then a circular wait can't happen. Whoever gets lock 1 first will finish.

A common trick is to sort by something unique, like an ID, and lock in that order.

Other options: use tryLock with a timeout so a thread gives up and retries instead of waiting forever, or hold locks for less time."

↳ Level 2 — "Two users transfer money to each other at the same time. Show me."

"This is the textbook case. transfer(A→B) and transfer(B→A) running together will deadlock if each locks in argument order.

void transfer(Account from, Account to, BigDecimal amount) {
    // decide order by ID, not by argument position
    Account first  = from.id().compareTo(to.id()) < 0 ? from : to;
    Account second = (first == from) ? to : from;

    synchronized (first) {
        synchronized (second) {
            from.debit(amount);
            to.credit(amount);
        }
    }
}

Now both threads lock the lower ID first, so one waits politely and neither gets stuck.

One edge case to mention: if someone transfers to themselves, from and to are the same account — I'd guard against that separately."

If you want to really impress, add: "though in a real banking system I wouldn't use Java locks at all — there's more than one server running, so a lock inside one JVM protects nothing. I'd put it in the database with a transaction and a version check."

Q88Explain the producer–consumer problem.

Your answer — "One or more threads produce items. Others consume them. They share a queue in the middle. The producer must wait if the queue is full; the consumer must wait if it's empty."

↳ Level 1 — "How would you implement it?"

"I'd use ArrayBlockingQueue and let Java do the work:

BlockingQueue<Bet> queue = new ArrayBlockingQueue<>(1000);

queue.put(bet);           // producer — waits automatically if full
Bet bet = queue.take();   // consumer — waits automatically if empty

put and take handle all the waiting and waking for me. There's no reason to write this by hand.

The size limit matters too — it means if consumers fall behind, producers naturally slow down instead of filling up memory."

↳ Level 2 — "Write it by hand with wait and notify."

public synchronized void put(Bet b) throws InterruptedException {
    while (queue.size() == capacity) wait();   // while, not if
    queue.add(b);
    notifyAll();
}

public synchronized Bet take() throws InterruptedException {
    while (queue.isEmpty()) wait();
    Bet b = queue.poll();
    notifyAll();
    return b;
}

"Three things they're checking here:

  • while, never if. A thread can wake up without anyone waking it — that's a real thing, called a spurious wakeup. Also another thread might grab the item first. So on waking, always re-check the condition.
  • notifyAll, not notify. With both producers and consumers waiting, notify might wake the wrong kind — a producer waking another producer while the queue is still full. Then everyone's stuck.
  • wait() releases the lock while waiting, which is the whole point. sleep() doesn't — it holds the lock and blocks everyone."

14.4 OOP and core Java

Q89Interface or abstract class — when do you use each?

Your answer — "An interface says what something can do. An abstract class says what it can do and shares some of the how. The biggest practical difference: a class can implement many interfaces but extend only one class."

↳ Level 1 — "Java 8 added default methods to interfaces. So what's left?"

"State. That's the real remaining difference.

An interface can now carry behaviour, through default methods. But it still can't hold instance fields, and it has no constructor.

So: if the subclasses need to share actual data and a construction process, I use an abstract class. If I'm just describing a capability — something is comparable, or payable — I use an interface."

↳ Level 2 — "What if a class implements two interfaces with the same default method?"

"It won't compile. Java makes you resolve it yourself, so there's no silent guessing:

class MyClass implements A, B {
    @Override public void doThing() {
        A.super.doThing();   // pick one explicitly
    }
}

That's Java deliberately avoiding the multiple-inheritance mess that C++ has. You can inherit behaviour from several places, but if there's a genuine conflict, you must say what you mean."

Q90Checked or unchecked exceptions?

Your answer — "Checked exceptions have to be handled or declared — the compiler forces it. Unchecked ones don't. Checked are meant for problems the caller could realistically recover from; unchecked for programming mistakes."

↳ Level 1 — "Which do you prefer in practice?"

"I lean towards unchecked in service code, and I'd say why rather than just assert it:

  • Checked exceptions leak implementation details upwards. If my repository throws SQLException, suddenly every layer above knows I'm using a database.
  • They don't work well with lambdas and streams — you end up wrapping everything anyway.
  • In real codebases they get caught and ignored just to make the compiler quiet, which is worse than not having them.

So I use a small set of my own unchecked exceptions and handle them all in one place at the edge — in Spring that's a @RestControllerAdvice."

↳ Level 2 — "What happens if you return from a finally block?"

"It silently throws away the exception.

try {
    throw new RuntimeException("something broke");
} finally {
    return "ok";   // the exception vanishes. No trace. Nothing logged.
}

The caller gets 'ok' and never knows anything went wrong. So: never return from finally.

Related — this is exactly why try-with-resources is better than closing things by hand. If both the body and the close fail, it keeps the real exception and attaches the close failure to it, rather than losing one."

Q91What are streams in Java 8?

Your answer — "A way to describe what you want from a collection instead of writing the loop yourself. Filter, transform, collect. It reads closer to the intent."

List<String> names = users.stream()
    .filter(u -> u.age() > 18)
    .map(User::name)
    .toList();

↳ Level 1 — "What does 'lazy' mean here?"

"Nothing runs until the end.

filter and map don't do any work when you call them — they just record what you asked for. Only a terminal operation like toList() or collect() actually triggers it.

This means Java can be clever. It processes each element through the whole chain at once, rather than making a new intermediate list at every step. And with something like findFirst(), it can stop as soon as it has an answer instead of processing everything."

↳ Level 2 — "Should you use parallelStream() to make it faster?"

"Usually not, and I'd be careful with it.

Three reasons:

  • It uses one shared thread pool for the entire application. If I put slow work or database calls on it, I slow down everything else that uses it.
  • Splitting the work and recombining costs something. For small collections, parallel is slower than sequential.
  • If my lambda touches shared mutable state, parallel turns a working program into a broken one.

It's worth it for genuinely large collections doing genuinely CPU-heavy work, with no shared state — and I'd measure before and after rather than assume."

14.5 Spring, database and APIs

Q92What does Spring Boot actually do for you?

Your answer — "It removes configuration. It looks at what libraries are on your classpath and sets up sensible defaults automatically. Put a database driver in, and it configures a connection pool without you writing any XML."

↳ Level 1 — "How does it know what to configure?"

"It has a list of configuration classes, and each one has conditions attached.

A typical condition is: 'only apply this if this class is on the classpath, and the user hasn't already defined their own version.'

That second part is the important one. If I define my own bean, Spring Boot backs off. That's why it feels like helpful defaults rather than magic you have to fight."

↳ Level 2 — "Something isn't being configured. How do you debug it?"

"Start the app with --debug. Spring Boot prints a Conditions Evaluation Report — a full list of every auto-configuration it considered, which ones were applied, which weren't, and the reason for each.

So instead of guessing, it tells me directly: 'did not match because DataSource class was not found', or 'did not match because you already defined this bean'."

Knowing the debugging move is worth more than knowing the definition. Most candidates can define auto-configuration; far fewer can say how to see inside it.

Q93What does @Transactional do?

Your answer — "It wraps the method in a database transaction. If the method finishes normally, everything commits. If it throws, everything rolls back. So either all the changes happen or none do."

↳ Level 1 — "How does Spring make that happen?"

"It creates a proxy — a wrapper object around my bean. Calls go to the wrapper first. The wrapper opens a transaction, calls my real method, then commits or rolls back.

My own code doesn't contain any transaction handling at all, which is the point."

↳ Level 2 — "Name a case where @Transactional silently does nothing."

"Three, and they're all silent — no error, it just doesn't work:

  1. Calling it from inside the same class. If method A calls method B in the same object, the call never goes through the proxy — it goes straight to the method. So @Transactional on B is ignored.
  2. Private methods. The proxy can't intercept them. Ignored.
  3. Checked exceptions. By default Spring only rolls back on unchecked exceptions. Throw a checked exception expecting a rollback and it will commit instead. You have to write @Transactional(rollbackFor = Exception.class).

That third one is nasty, because it fails in the direction of keeping bad data."

Q94What is the N+1 problem?

Your answer — "You run one query to fetch a list, then accidentally run one more query for every item in that list. Fetch 100 customers and then touch their orders, and you've done 101 database round trips instead of 1."

↳ Level 1 — "Why does it happen?"

"Because relationships are lazy by default, which is usually the right choice. The orders aren't loaded with the customer — they're loaded the moment you first touch them.

Inside a loop, that means one query per iteration. Nothing in the code looks wrong. It passes every test with three rows and then destroys production with ten thousand."

↳ Level 2 — "How do you fix it, and how would you catch it before production?"

"Fixing it is easy — use JOIN FETCH in the query, or @EntityGraph on the repository method, and it becomes one query with a join.

Catching it is the more interesting half. Reading SQL logs by eye doesn't scale — nobody does it consistently.

So I'd have tests that actually count the queries, using Hibernate statistics or a datasource proxy, and fail if the number goes up. That way the build catches it when someone adds a lazy field, instead of a customer finding it."

That answer — "here's the fix, and here's how I stop it coming back" — is a level above just naming JOIN FETCH.

Q95Write a query to find the second-highest salary.

Your answer — start with the simple one:

SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

"Find the highest, then find the highest of everything below it."

↳ Level 1 — "Now give me the third highest. And the Nth."

"The subquery trick doesn't extend well, so I'd switch to a window function:

SELECT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
  FROM employees
) t WHERE rnk = 3;

Change the number and it works for any position."

↳ Level 2 — "What's the difference between ROW_NUMBER, RANK and DENSE_RANK?"

"It's all about how they handle ties. Say salaries are 100, 90, 90, 80:

FunctionResultBehaviour
ROW_NUMBER1, 2, 3, 4Always unique. Ties broken arbitrarily.
RANK1, 2, 2, 4Ties share a rank, then it skips a number.
DENSE_RANK1, 2, 2, 3Ties share a rank, no gap.

So for 'second highest distinct salary' I want DENSE_RANK. With RANK, asking for rank 3 would return nothing at all in that example."

Q96How do you make an API idempotent?

Your answer — "Idempotent means calling it twice has the same effect as calling it once. It matters because networks fail. If a customer places a bet and the response is lost, their app retries — and you must not take the money twice."

↳ Level 1 — "How would you build that?"

"The client generates a unique ID for the operation and sends it as a header. If it retries, it sends the same ID.

On my side I store that ID in a table with a unique constraint.

  • First request: the insert succeeds, I process the bet, and I save the response.
  • Retry: the insert fails because of the unique constraint. So I know I've seen it — I return the saved response and do nothing else.

↳ Level 2 — "Why a database constraint? Couldn't you just check Redis?"

"Checking first and then acting leaves a gap. Two retries can arrive at the same instant, both check, both see nothing, and both process. That's exactly the bug I was trying to prevent.

A unique constraint has no gap. The database decides, and only one insert can win. There's no window between checking and acting.

I'd still use Redis in front of it as a fast path to avoid hitting the database for obvious duplicates. But the actual guarantee lives in the database. Redis is the optimisation; the constraint is the correctness."

This is a very likely question at a betting company — taking money twice is their worst-case bug. If you only rehearse three answers from this section, make this one of them.

14.6 When they make you write code

Q97Find two numbers in an array that add up to a target.

Say this before you type — "The obvious way is two nested loops, checking every pair. That works but it's O(n²). I can do it in one pass with a HashMap instead, trading some memory for speed."

static int[] twoSum(int[] nums, int target) {
    Map<Integer, Integer> seen = new HashMap<>();   // value -> position
    for (int i = 0; i < nums.length; i++) {
        Integer j = seen.get(target - nums[i]);
        if (j != null) return new int[]{j, i};
        seen.put(nums[i], i);                         // store AFTER checking
    }
    return new int[0];
}

↳ Level 1 — "Explain how that works."

"For each number I work out what its partner would need to be — target minus this number. Then I check whether I've already seen that partner.

If yes, I'm done. If no, I remember this number and move on.

Each number is looked at once, and HashMap lookups are instant, so it's O(n) time and O(n) space."

↳ Level 2 — "Why do you store the number after checking, not before?"

"Because otherwise a number could match with itself.

If the target is 10 and the current number is 5, then storing first means I immediately find 5 in the map — but that's the same 5 I'm standing on, not a different one. I'd return a wrong answer using one element twice.

Checking first means the map only ever contains numbers from earlier positions."

This is the exact question interviewers use to see whether you understood your own code or memorised it. Have the answer ready.

Q98Reverse a string.

Your answer — "One line: new StringBuilder(s).reverse().toString(). But if you want me to write it manually, I'd use two pointers."

static String reverse(String s) {
    char[] c = s.toCharArray();
    int i = 0, j = c.length - 1;
    while (i < j) {
        char t = c[i]; c[i] = c[j]; c[j] = t;
        i++; j--;
    }
    return new String(c);
}

↳ Level 1 — "Why convert to a char array at all?"

"Because String is immutable — I can't change its characters. So I copy them into an array I can change, swap them, then build a new String from the result.

One pointer starts at each end, they swap and move towards the middle, and they stop when they meet. That's O(n) time, and each character is touched once."

↳ Level 2 — "Does your solution work for emoji?"

"No — and neither does the one-line version. That's a good catch.

Java stores text as UTF-16. Most characters fit in one unit, but emoji and some other symbols take two units together, called a surrogate pair. If I reverse blindly, I split those pairs apart and get broken output.

The proper fix is to work in code points rather than char values.

In practice I'd ask what the input actually is. If it's a bet reference or an ID, the simple version is correct and clear. If it's user-entered text, I need the code-point-aware version."

Saying "it depends what the input is" is a genuinely senior answer. It shows you weigh correctness against complexity rather than always reaching for the most complicated option.

15.1 Event-driven architecture

Q99What is event-driven architecture, and why use it?

Your answer — "Instead of services calling each other directly, a service announces that something happened and carries on. Anyone interested listens. The publisher doesn't know or care who's listening."

The contrast to draw:

Request–responseEvent-driven
CouplingCaller must know the calleePublisher knows nothing about consumers
Adding a featureChange the callerAdd a new consumer, change nothing existing
If downstream is downYour call failsEvent waits in the log; consumer catches up later
ConsistencyImmediateEventual
DebuggingEasy — one stack traceHarder — needs tracing and correlation IDs

The betting example makes it concrete: "When a bet is placed, I publish one BetPlaced event. The risk engine, CRM, reporting, and settlement all consume it independently. If marketing wants a new 'first bet of the day' campaign, they add a consumer — I don't touch the bet service at all. That's the real payoff: adding features without modifying working code."

Always say the cost too. "The trade-off is eventual consistency. For a moment after the bet, the reporting system doesn't know about it yet. That's fine for reporting. It is not fine for the balance check that decides whether the bet is allowed — that has to be synchronous and transactional. Knowing which side of that line a piece of logic belongs on is the actual skill."

Q100Event vs command vs message — do you know the difference?

  • Event — a fact about the past. BetPlaced, PaymentReceived. Past tense. It already happened; you cannot reject it. Zero or many consumers.
  • Command — an instruction. PlaceBet, RefundPayment. Imperative. Exactly one handler, and it can refuse.
  • Message — the generic envelope either travels in.

Why it matters in practice: "naming matters more than it sounds. If I publish something called SendEmail to a topic, I've written a command dressed as an event — I've secretly coupled myself to the email service and its behaviour. If I publish BetSettled, the email service can decide for itself whether to act. The past-tense name is what keeps the publisher decoupled."

Q101You save to the database and publish an event. How do you make sure both happen?

This is the single most likely event-driven question, and it has a named answer: the transactional outbox.

The problem first — "I can't put a database write and a Kafka publish in one transaction. They're different systems. So there are two ways to fail:

  • DB commits, publish fails → the bet exists but nothing downstream knows. Silent data loss.
  • Publish succeeds, DB rolls back → downstream acts on a bet that doesn't exist. Worse.

↳ The outbox pattern:

  1. In one database transaction, write the bet row and insert a row into an outbox table. Both or neither — the database guarantees it.
  2. A separate process reads unpublished outbox rows and publishes them to Kafka.
  3. On success, mark the row published.

"If the publisher crashes mid-way, the row is still there and gets picked up again. That means at-least-once delivery — so consumers must be idempotent. But nothing is ever lost, and nothing is ever published for a transaction that rolled back."

Level 2 — "How does the publisher read the outbox?" Two ways. Polling — simple, a query every few hundred milliseconds, fine for most systems. Change Data Capture — a tool like Debezium tails the database's own transaction log, which adds no query load and gives lower latency, at the cost of running more infrastructure. Start with polling; move to CDC when the poll cost or the latency actually hurts.

Q102How do you handle a business transaction spanning several services?

The Saga pattern. "You can't hold a database transaction across services. So instead of one big transaction, you run a sequence of local transactions, and if one fails you run compensating actions to undo the earlier ones."

Two flavours — know both:

  • Choreography — each service listens for the previous event and emits the next. No central controller. Simple with 2–3 steps; becomes impossible to follow with 7, because the flow exists nowhere in the code.
  • Orchestration — one coordinator explicitly drives each step and handles failures. More moving parts, but the whole flow is written down in one place. Prefer this once the flow is non-trivial.

The betting example: "Place bet → reserve funds → confirm bet → notify. If confirming the bet fails, the compensating action is to release the reserved funds. Note it's a compensation, not a rollback — the reservation genuinely happened and stays in the ledger as a reversal, which is what auditors want anyway."

The honest caveat — "there's no isolation in a saga. Another process can see the intermediate state, where funds are reserved but the bet isn't confirmed. You design for that explicitly — usually with a status field and by making the intermediate state meaningful rather than pretending it doesn't exist."

Q103Event-driven vs event sourcing vs CQRS — are they the same thing?

No, and mixing them up is a common giveaway. They're three separate ideas that often appear together.

IdeaWhat it actually means
Event-drivenServices communicate by publishing events. About integration.
Event sourcingYou store the sequence of changes as the source of truth, not the current state. Current state is derived by replaying them. About storage.
CQRSSeparate model for writing and for reading. About modelling.

Event sourcing, made concrete: "Instead of a balance column that I overwrite, I store Deposited 100, BetPlaced 20, WinCredited 50. The balance is the sum: 130. I never lose history, I can rebuild the balance at any past moment, and I get a complete audit trail for free — which in a regulated gambling business is worth a great deal."

State the costs, because interviewers are wary of people who only sell the upside. "Event sourcing makes simple queries hard — 'show me all customers with balance over £500' now needs a separate read model, which is where CQRS comes in. You also have to version events forever, because a five-year-old event still has to be readable. I'd use it for the money ledger, where the audit trail justifies it. I would not use it for a user profile table."

Q104How do you guarantee ordering of events?

Your answer — "Ordering is guaranteed within a partition, never across a topic. So the question becomes: what do I need ordered? I pick that as the partition key."

"For a wallet, I key by customerId. Every event for one customer lands in the same partition, so that customer's events are strictly ordered. Different customers are in different partitions and can be processed in parallel. I get ordering exactly where it matters and parallelism everywhere else."

↳ Level 1 — "What if you need more throughput than one partition gives?"

"Then you have to accept that one customer's events can't go faster than one partition. That's usually fine — no single customer generates that much traffic. The system scales by having many partitions, not by making one fast.

If one key genuinely is too hot, that's a design smell — it usually means the key is too coarse."

↳ Level 2 — "Consumer processes events out of order anyway. Why?"

"Almost always because someone made processing multi-threaded inside the consumer. Kafka hands you an ordered batch, and then a thread pool processes them concurrently and destroys the ordering you paid for.

The fix is to keep one thread per partition, or to shard the internal work by the same key so a given key is always handled by the same thread.

The other cause is a retry — a failed message going to a retry topic and coming back later, after messages that followed it. That's a real trade-off: strict ordering versus not blocking the partition on one bad message. You pick one deliberately."

Q105A consumer keeps failing on one message. What happens?

"It's a poison message, and if you don't handle it, it blocks the whole partition. The consumer retries forever, lag climbs, and every message behind it is stuck — one bad record takes down a feature."

The handling chain:

  1. Retry a few times with backoff — for genuinely transient failures like a brief network blip.
  2. Then move it to a retry topic, so the main partition isn't blocked while you wait.
  3. After N attempts, send it to a dead-letter topic with the failure reason and attempt count in the headers.
  4. Alert on the DLT. A dead-letter queue nobody monitors is just a place where data goes to die quietly.
  5. Be able to replay from it once the bug is fixed.

The distinction to draw — "I'd separate retryable from non-retryable failures. A timeout calling another service is worth retrying. A message that fails validation will fail identically a thousand times, so it should go straight to the DLT without burning retries. Retrying a permanent failure is just a slower way to lose the message."

Q106How do you change an event's structure without breaking consumers?

Schema evolution. "Once an event is published, someone is reading it and you don't control their deployment schedule. So the rules are strict:"

  • Safe: adding an optional field with a default. Old consumers ignore it.
  • Unsafe: removing a field, renaming a field, changing a type, or making an optional field required. Any of these breaks consumers that haven't updated.
  • For a real change: publish a new version alongside the old, migrate consumers, then retire the old one. Never a flag-day switch.

"In practice I'd use a schema registry with Avro or Protobuf. It enforces compatibility at publish time — if I try to push a breaking change, it's rejected before it ever reaches a consumer. That turns a production incident into a build failure, which is exactly where you want it."

The event-sourcing wrinkle — "with event sourcing this gets harder, because you have to be able to read events written five years ago, forever. You can't just retire an old version. That's a real long-term cost people underestimate."

15.2 WebSocket

Q107What is a WebSocket and when would you use one?

Your answer — "A persistent two-way connection between browser and server. Normal HTTP is request–response: the client asks, the server answers, connection done. With a WebSocket the connection stays open and the server can send data without being asked."

How it starts: "It begins as a normal HTTP request with an Upgrade: websocket header. The server replies 101 Switching Protocols, and from that point it's no longer HTTP — it's a raw two-way message channel over the same TCP connection. That's why it works through firewalls and on port 443."

The comparison they'll want:

ApproachDirectionUse when
PollingClient asks repeatedlyAlmost never. Wasteful and always late.
Long pollingClient asks, server holdsLegacy fallback only
SSEServer → client onlyYou only need to push. Simpler, auto-reconnects, plain HTTP.
WebSocketBoth waysClient also sends frequently — live betting, chat, live casino

The mature answer — "I'd ask whether I actually need two-way. For pushing odds updates to a screen, SSE does the job with less operational pain: it's plain HTTP, it reconnects by itself, and proxies understand it. I'd pick WebSocket when the client genuinely sends a lot too — placing bets in-play, or live casino where the player is acting continuously." Saying "I'd consider the simpler option" is a strong signal, not a weak one.

Q108How do you scale WebSockets across many servers?

The core problem first — "HTTP is stateless, so any server can serve any request. WebSockets are stateful: the connection lives on one specific server. If an odds update arrives at server 2 but the customer is connected to server 5, server 2 has no way to reach them."

The two pieces of the answer:

  1. Sticky sessions at the load balancer — once connected, that client keeps going to the same server. Necessary, but not sufficient, and it makes deploys harder.
  2. A pub/sub backplane — this is the real answer. Every server subscribes to a shared channel (Redis pub/sub, Kafka, or NATS). When an odds change happens anywhere, it's published once; every server receives it and forwards it to whichever clients it holds. No server needs to know where anyone is connected.

↳ Level 1 — "What happens when you deploy?"

"Every connection on that server drops at once, and all those clients reconnect simultaneously — a thundering herd against the remaining servers.

So you drain gracefully: stop accepting new connections, tell existing clients to reconnect over a spread-out window, then shut down. And clients reconnect with jitter, not instantly, or you just move the spike."

↳ Level 2 — "How does the client not miss messages while reconnecting?"

"Sequence numbers. Every message carries one. On reconnect, the client says 'I last saw 4,182' and the server sends what it missed, or tells it to resync from a fresh snapshot if the gap is too big.

Without that, a customer reconnects and silently has stale odds — which in betting is a real financial problem, not a cosmetic one."

Q109A client is slow to read. What happens to your server?

This is the question that connects WebSockets to §6, and it's a great one to answer well.

"You keep writing messages to that connection. The client isn't reading them. They queue in an outbound buffer in your heap. Multiply that by a few thousand slow mobile connections on poor networks and you've got an OutOfMemoryError — caused not by your code but by other people's bad wifi."

The fixes:

  • Bound the per-connection buffer. When it's full, disconnect that client. They reconnect and resync. Losing one slow client is infinitely better than losing the server for everyone.
  • Conflate messages. If odds changed five times while they were behind, send the latest value, not all five. For state updates, only the current value matters — this is the single biggest win.
  • Monitor buffer depth as a first-class metric, not just connection count.

Conflation is worth emphasising: "it's the difference between a queue of changes and a slot holding current state. For a live price feed, the second is almost always what you actually want, and it makes slow consumers a non-problem."

Q110How do you authenticate a WebSocket?

  • Authenticate at the handshake, before the upgrade. Once it's open there's no per-message HTTP layer to check.
  • Don't rely on cookies — browsers don't apply the same-origin policy to WebSockets the way they do to HTTP, which opens up cross-site WebSocket hijacking. Validate the Origin header server-side, always.
  • Pass a short-lived token. Avoid putting it in the URL query string — URLs end up in access logs and proxy logs. A common pattern is a one-time ticket: fetch it over normal authenticated HTTP, then present it on connect.
  • Handle expiry on a long-lived connection. A connection open for six hours outlives its token. Either re-authenticate periodically over the socket, or close and make the client reconnect.

The Origin check is the one candidates miss, and it's a genuine vulnerability — worth saying explicitly at a company that handles customer money.

Q111How do you know a connection is still alive?

"TCP will happily hold a connection open that's actually dead — the classic case is a phone going into a tunnel. The server thinks the customer is connected; they're not.

So you use ping/pong frames, which are built into the protocol. The server pings every 30 seconds or so; if there's no pong within a timeout, the connection is dead and gets closed and cleaned up.

It also keeps intermediate proxies and load balancers from closing an idle connection — many have a 60-second idle timeout, and heartbeats keep the connection looking busy."

"On the client side, the matching behaviour is reconnect with exponential backoff and jitter. Without jitter, a server restart means every client reconnects at the same instant and knocks it over again."

Q112How would you do this in Spring?

"Spring supports it directly. Two levels:

  • Raw — implement WebSocketHandler and register it. Full control, you handle everything.
  • STOMP over WebSocket — @EnableWebSocketMessageBroker gives you a messaging layer on top, with subscribe/publish semantics, destinations like /topic/odds/market-123, and @MessageMapping methods that look like controllers.

For real scale you point STOMP at an external broker rather than the simple in-memory one, which is what gives you the backplane from Q108."

@Configuration
@EnableWebSocketMessageBroker
class WsConfig implements WebSocketMessageBrokerConfigurer {
    public void configureMessageBroker(MessageBrokerRegistry r) {
        r.enableSimpleBroker("/topic");        // swap for a real broker at scale
        r.setApplicationDestinationPrefixes("/app");
    }
    public void registerStompEndpoints(StompEndpointRegistry r) {
        r.addEndpoint("/ws").setAllowedOrigins("https://example.com");
    }
}

If they ask about reactive: "with WebFlux you'd use the reactive WebSocketHandler, where the session is a Flux of messages. That gives you back-pressure as a first-class concept rather than something you bolt on — which directly addresses Q109."

Q116How do you make an application on AWS highly available?

  • Multi-AZ, always. Availability Zones are physically separate data centres in one region. Spread across at least two — this is the single highest-value thing you do.
  • Load balancer in front, with health checks that actually test the app rather than just returning 200 from a static endpoint.
  • Auto-scaling on a meaningful metric. For a betting platform, load is spiky and event-driven — a big race or match creates a sharp peak. Scheduled scaling ahead of known events matters as much as reactive scaling.
  • Aurora Multi-AZ with automatic failover, plus read replicas to take read load off the writer.
  • Stateless application servers so any instance can be replaced. Push session state to ElastiCache.
  • Multi-region only if you genuinely need it — it's a large jump in cost and complexity, and it forces you to confront data-residency rules (Q117).

The distinction to draw: "high availability and disaster recovery aren't the same thing. Multi-AZ handles a data centre failing. It does not protect you from someone deploying a bad migration that corrupts the database — that's what backups and point-in-time recovery are for. I'd want both, and I'd want the restore tested, because a backup you've never restored isn't a backup."

Q117★ What's special about running a gambling platform on the cloud?

Regulation. This is the answer that shows you understand their industry, not just AWS.

  • Data residency. Many gambling regulators require that customer and transaction data stays physically inside their jurisdiction. That's a hard architectural constraint: you can't just run one global cluster. It pushes you toward region-per-market deployments, which is a big part of why Entain runs a proprietary platform deployed many times over.
  • Audit trail. Regulators expect a complete, immutable record of every bet and every money movement, retained for years. That is a strong argument for an append-only ledger and event sourcing (Q103).
  • Certification. RNGs and game logic must be certified by approved testing houses. That means you cannot hot-fix game logic the way you would a normal service — changes go through re-certification. It genuinely changes your release process.
  • Responsible gambling. Deposit limits, self-exclusion and affordability checks are legally required and must work reliably. A self-exclusion that fails to apply isn't a bug, it's a regulatory breach.
  • Segregation of duties. Tight IAM, least privilege, and developers generally not holding production data access.

Even one of these said well — most naturally data residency — marks you out as someone who's thought about their problem rather than reciting cloud generalities. It's one of the highest-leverage things you can say in this round.

Q118How do you handle secrets and permissions on AWS?

  • Never hardcode credentials. No access keys in code, config files, or environment variables committed to git.
  • Use IAM roles. On EKS that's IAM Roles for Service Accounts (IRSA) — the pod assumes a role and gets short-lived, automatically rotated credentials. Nothing to leak.
  • Secrets Manager or Parameter Store for database passwords and third-party API keys, with automatic rotation where supported.
  • Least privilege. Grant the specific actions on the specific resources. Start closed and open up, rather than starting with * and intending to tighten later — which never happens.
  • Separate accounts per environment. Production in its own AWS account so a mistake in dev cannot touch it.

If asked what you'd check first in a security review: "whether anything is using long-lived access keys, and whether any policy has Action: * on Resource: *. Those two find most of the real problems."

Q119Kubernetes — what do you actually need to know?

Entain's platform is built on EKS, so this is more likely than exotic AWS trivia. You don't need to be an SRE — you need to sound like someone who ships to Kubernetes and understands why things break.

  • Pod — the smallest unit, one or more containers together. Deployment — manages replicas and rolling updates. Service — a stable address in front of changing pods. Ingress — routes outside traffic in.
  • ConfigMap / Secret — configuration and credentials injected at runtime, not baked into the image.
  • Liveness vs readiness probes — this distinction is the one that gets asked. Liveness failing restarts the pod. Readiness failing just takes it out of the load balancer without killing it. Getting these the wrong way round causes restart loops during slow startup.
  • Requests and limits — and this is where it meets §6: if your container's memory limit is 2 GB and you set -Xmx2g, you will be OOM-killed, because heap isn't the whole process. Leave 25–30% headroom, or use -XX:MaxRAMPercentage.
  • HPA — Horizontal Pod Autoscaler, scaling on CPU or custom metrics.

The exit-code-137 story is a great thing to have ready — "a pod restarting with 137 and no Java stack trace means the kernel killed it, not the JVM. That's a container memory budgeting problem, and no heap dump will exist. I'd go to native memory tracking, not to MAT." That single answer ties memory management, containers and production debugging together, which is exactly the level they're probing for.

Q120How do you debug a problem across many services?

The three pillars, and what each is for — logs (what happened), metrics (how much and how fast), traces (where the time went). You need all three; they answer different questions.

  • Correlation / trace ID — generated at the edge, passed through every service and into every log line and every event published. Without it, cross-service debugging is guesswork. This is the single most important item on the list.
  • Structured logging — JSON, not free text, so you can actually query it.
  • Distributed tracing — OpenTelemetry, X-Ray or Jaeger, to see the full call chain and find which hop is slow.
  • Metrics with percentiles — p95 and p99, never averages. An average hides the fact that 1% of customers are having a terrible time, and at scale 1% is a lot of people.
  • Alert on symptoms, not causes — alert on error rate and latency that customers feel, not on CPU being at 80%.

Tie it to event-driven, because that's what they asked about: "this matters more in an event-driven system, not less. There's no single stack trace to read — a bet leads to five consumers reacting independently. If the trace ID isn't carried in the event headers, you simply cannot follow what happened. I'd treat that as part of the event envelope, not an afterthought."

15.4 Casino architecture

The topic you have least on, and the one where a specific answer will stand out most. Learn the vocabulary — RGS, PAM, aggregator, seamless wallet, game round. Using the right words signals domain awareness instantly.

Q121★ Walk me through the architecture of an online casino.

Start with the key insight, which surprises most people: "the operator usually doesn't write the games. Games come from studios like Pragmatic Play or Light & Wonder. The operator's job is the platform around them — accounts, money, sessions, compliance — and the integration layer that connects to game providers."

Q122★ Seamless wallet vs transfer wallet — explain the difference.

This is the central concept in casino integration. Know it cold.

Transfer walletSeamless wallet
How it worksPlayer moves money into the game provider before playing, and back out afterBalance stays with the operator; the provider calls the operator for every bet and win
Source of truthSplit between two systemsOne authoritative balance — the operator's
Player experienceClunky — visible transfer stepSeamless — one balance everywhere
Engineering loadLower, but reconciliation is painfulMuch higher — you're on the hot path of every single spin

Seamless is the modern standard, and it's what makes this an interesting engineering problem:

  1. Player spins. The provider's RGS calls your wallet API: debit — take the stake.
  2. RGS runs the game and decides the outcome using its RNG.
  3. RGS calls your wallet again: credit — pay the win (possibly zero).
  4. Round closes.

Now the implications, which is what they're really asking about:

  • Your wallet is on the critical path of every spin at every casino, from every provider. It must be fast and it must never be wrong. Latency here is felt directly by the player.
  • If your wallet is down, every casino game stops — not just one.
  • Every one of those calls can time out and be retried. So every endpoint must be idempotent (Q123).

Q123★ The provider calls debit, times out, and retries. How do you not take the money twice?

The single most likely casino question, and it's your idempotency answer (§8 Q47, §14 Q96) applied to this domain.

"Every call from the provider carries a transaction ID, and every round carries a round ID. I store the transaction ID with a unique constraint in the database.

  • First call: the insert succeeds, I debit the balance, I record the result.
  • Retry with the same transaction ID: the insert fails on the constraint. So I know I've already done it — I return the same response as before, including the same resulting balance, and I do not touch the balance again.

The critical detail: on a duplicate I must return success with the original result, not an error. If I return an error the provider may think the bet failed and roll it back, and now the player's balance is wrong in the other direction."

↳ Level 1 — "Why a database constraint rather than checking first?"

"Because 'check then act' has a gap. Two retries arriving at the same moment both check, both see nothing, both proceed. The unique constraint has no gap — the database serialises it and exactly one wins."

↳ Level 2 — "What about rollback?"

"Providers send a rollback when a round fails — the game crashed after the debit, say. That must also be idempotent, keyed on the original transaction ID, and it must be safe to receive out of order: a rollback can arrive for a transaction you haven't seen yet, because the debit request timed out on their side but never reached you.

The standard handling is to record the rollback anyway, so that if the debit arrives afterwards you already know it's void. Getting that ordering case right is what separates a real implementation from a naive one.

And the trickiest case: rolling back an already-settled round. You can't just subtract — the balance may have moved since. It goes in the ledger as a compensating entry, never as an edit to history."

Finish with the ledger principle: "I'd never store balance as a mutable number I overwrite. I'd store immutable ledger entries and treat the balance as their sum, cached for speed. That way every movement is auditable and reversible by addition, which is exactly what regulators and reconciliation both need."

Q124What is a game round and why does it need its own ID?

"A round is one complete play — one spin, one hand. It can involve several money movements: a debit for the stake, possibly more debits if the player buys extra features, then a credit for the win. Free spins can make one round span minutes.

The round ID ties them together. Without it you have a pile of unrelated debits and credits and no way to answer 'what happened in this spin?'

You need it for:

  • Reconciliation — matching your ledger against the provider's report at end of day. This is a daily operational reality, not a theoretical concern.
  • Disputes — a player says they won and weren't paid. You need the full round.
  • Regulatory audit — regulators ask for complete round histories.
  • Knowing a round is still open — you can't let a player withdraw funds mid-round, and you need to handle rounds abandoned when someone closes the browser."

The open-round problem is a good thing to raise unprompted — "a player can close the tab mid-round. The round stays open forever unless something closes it. So you need a timeout and a reconciliation job that finds stale rounds and settles or voids them against the provider's record."

Q125Where does the RNG live and why does that matter?

  • It lives in the provider's RGS, not in your platform. The game studio owns the outcome. You own the money.
  • It must be a cryptographically secure generator — in Java terms, SecureRandom, never Math.random() or plain Random. A predictable generator is an exploitable one.
  • It is certified by an independent testing house (GLI, eCOGRA and similar) and tested for statistical randomness and for the game's declared return-to-player percentage.

The consequence worth stating, because it's a real engineering constraint: "certification means game logic can't be hot-fixed. A change to anything affecting outcomes goes back through certification before it can be released. So the release process for game logic is fundamentally different from a normal service — and that's one reason the platform and the games are kept firmly separated."

If they mention provably fair: "that's a different model, common in crypto casinos, where a server seed is committed as a hash up front and revealed later so the player can verify the result wasn't changed after their bet. Regulated operators generally rely on certified RNG and audit instead."

Q126How would you build a progressive jackpot?

"A progressive jackpot grows as a small percentage of every bet across many players and many games, then pays out once. It's a shared counter under very high concurrency — a genuinely interesting distributed systems problem."

The design:

  • Contribution — every bet adds a small amount. Very high write rate, so a single row with a lock becomes a bottleneck immediately. Options: an in-memory counter flushed periodically, or a striped counter summed on read (this is exactly LongAdder's idea from §7 Q25, applied at system scale).
  • Display — the ticking number players see is pushed over WebSocket (§15.2) and doesn't need to be perfectly exact. Nice link to make.
  • The award — this is the hard part and must be exactly once. Two players cannot both win the same pot. Use a conditional update: atomically mark the jackpot as won and capture the amount in one operation. Whoever loses that race doesn't win.
  • Reset and seed — the pot resets to a seed value funded from contributions.

The distinction to make explicitly — "the displayed value can be approximate and eventually consistent; nobody is harmed if it's a few pence behind. The awarded value must be exact and atomic. Knowing which parts of a system need strict consistency and which don't is most of the design work here." That sentence is the answer they're looking for.

Q127How do bonuses and free spins complicate the wallet?

"They turn one balance into several, and the rules are legally significant.

  • Separate balances — real money and bonus money must be tracked separately, because bonus funds usually can't be withdrawn until wagering requirements are met.
  • Spend order — which balance is used first is a business rule with regulatory implications, and it must be consistent and auditable.
  • Wagering requirements — 'wager 30× the bonus before withdrawal'. That means tracking qualifying turnover per bonus, and different games can contribute at different rates.
  • Eligibility — some games are excluded from bonus play entirely.
  • Expiry — bonuses expire, and the remaining balance must be removed correctly.

The framing that shows judgement: "this is where a lot of real complexity and a lot of real bugs live, because it's business rules layered on top of money. I'd want it as an explicit bonus engine with its own state machine and a full audit trail, not as conditionals scattered through the wallet service. If a bonus is applied wrongly you either lose money or mistreat a customer, and both end up in front of a regulator."

Q128The game provider's API is slow or down. What do you do?

"Two directions, and they're not symmetric — worth separating them explicitly:

They call me (seamless wallet — the critical direction):

  • My wallet must be fast and highly available, because it's on the path of every spin. Tight latency budget, multi-AZ, no single point of failure.
  • I can't shed this load — refusing a wallet call means the player's spin fails.

I call them (launching a game, fetching a catalogue):

  • Timeouts on everything, a circuit breaker per provider, and a bulkhead so one failing provider can't consume all my threads and take down the others.
  • Degrade gracefully — hide that provider's games from the lobby rather than showing a broken tile or failing the whole page.

The bulkhead point is the one to emphasise at an operator — "with many game providers integrated, the realistic failure isn't 'the casino is down', it's 'one studio is having a bad day'. Without isolation per provider, one slow integration degrades everything. With it, players lose ten games out of a thousand and never notice."

If pushed on the unhappy path: "if a round is left in an uncertain state because the provider timed out, I don't guess. The round stays open and pending, and it's resolved against the provider's authoritative record during reconciliation. Guessing in either direction either costs money or cheats a customer."

Q129How do you make the wallet fast enough?

"Every spin hits it, so this is a real scaling problem rather than a theoretical one.

  • Shard by customer. One customer's money only ever touches one shard, so there's no cross-shard transaction on the hot path. Customers are naturally independent, which makes this unusually clean.
  • Optimistic locking, not pessimistic. A version column and a retry, rather than holding a row lock. A pessimistic lock on a hot account becomes a throughput ceiling — and it's exactly the kind of thing that deadlocks (§14 Q87).
  • Keep the transaction tiny. No external calls inside it. Validate first, then do the shortest possible write.
  • Append-only ledger with the current balance cached or maintained as a projection — appends are cheaper and contend less than updates.
  • Everything else async. Reporting, CRM, analytics all consume events (§15.1) rather than sitting inside the critical transaction.

And the line that ties the whole interview together: "the constraint I'd hold onto is that the balance must never be wrong, even once. So anywhere I trade consistency for speed — caching a displayed balance, say — it has to be somewhere a stale value is harmless. Never on the debit path."

Q130★ Design the casino platform. Go.

If you get one big design question, this is the likeliest shape. A four-minute spoken skeleton:

  1. Clarify first. "Are we building the games, or integrating third-party providers?" — the answer is integrating, and asking shows you know the industry. Also ask: how many concurrent players, which jurisdictions, seamless or transfer wallet.
  2. Draw the boundary. Player → lobby → game launch → provider's RGS → callbacks into my wallet. Say clearly: game logic and RNG are theirs; accounts, money and compliance are mine.
  3. Core services. PAM, Wallet/Ledger, Lobby/Catalogue, Integration layer, Bonus engine, RG/compliance. Name the wallet as the critical one.
  4. The hot path in detail. Seamless wallet: debit → outcome → credit, with idempotency keys and round correlation. Spend your time here — it's the heart of the answer.
  5. Consistency choices, stated deliberately. Wallet is strongly consistent and transactional. Reporting, CRM and analytics are event-driven and eventually consistent. Say why each is on the side it's on.
  6. Real-time. WebSocket for jackpot tickers, live casino, and balance updates — with a pub/sub backplane to scale.
  7. Scale and resilience. Shard the wallet by customer; circuit breakers and bulkheads per provider; multi-AZ; autoscale for event-driven peaks.
  8. The bit most candidates forget. Data residency per jurisdiction, immutable audit trail, RNG certification constraints on releases, responsible-gambling enforcement, and daily reconciliation against provider reports.

Close on the trade-off, not on a list of boxes. "If I had to pick the single hardest constraint, it's that the wallet is synchronous, on the path of every spin, called by systems I don't control, over a network that fails — and it must never be wrong. Almost every design decision here comes out of that one sentence." Ending on the core tension is what makes it sound like experience rather than a memorised diagram.
